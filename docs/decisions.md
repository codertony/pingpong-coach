## D-001：新建独立仓库，而不是整体 fork

**日期**：2026-09-15
**状态**：已决定

| 方案 | 优点 | 主要代价 | 决定 |
| --- | --- | --- | --- |
| 整体 fork 乒乓球论文项目 `ttcs_by_llm` | 分析思路贴近需求 | 现有流程偏手动裁剪和批处理，实时前端、调度和验收仍要重做 | 用作方法参考 |
| 基于 Sports2D 改造 | 容易看到轨迹和角度 | 产品形态不同；二维结果受运动平面影响 | 用作独立验证工具 |
| **新建 Web 应用，集成 MediaPipe** | 与现有技能匹配，前后端分工简单，视觉本地运行 | 需要验证浏览器端高速动作识别质量 | **首选** |
| Python + rtmlib + Web UI | 模型选择和视觉实验更灵活 | 增加 Python 服务与部署工作 | 首选方案失效后的替代 |

论文代码的 README 显示其裁剪步骤需要手工选起止点，OpenPose 脚本遍历视频文件处理。因此借鉴方法比继承完整运行流程更合适。

## D-002：技术栈

**日期**：2026-09-15
**状态**：已实现

pnpm workspace + React/TypeScript + Vite + MediaPipe Tasks Vision（Worker 内运行）+ 纯 TypeScript motion-core + Zod contracts + Node/Fastify。

**理由**：
- 首版**不用** Nx/Turborepo，也不建立多服务编排平台。pnpm 原生 workspace 足以管理应用和共享包。
- 依赖方向固定：`contracts` 不依赖应用；`motion-core` 只依赖 `contracts` 与纯计算工具，不依赖 DOM/React/MediaPipe/数据库/网络；`web` 依赖 `contracts + motion-core`；`api` 依赖 `contracts`，且前端传来的数据必须再次校验。

**实测**：见 [evaluation-log.md](./evaluation-log.md)。pnpm 10.28.2 下 workspace 与 `workspace:*` 协议工作正常。

## D-003：MediaPipe 作为首版视觉底座

**日期**：2026-09-15
**状态**：已实现，质量未验证

`@mediapipe/tasks-vision` 的 Pose Landmarker，33 个关键点，Apache-2.0。

**已知需要验证的点**：
- MediaPipe Web 文档指出检测调用是**同步执行**的，会阻塞调用线程 → 已放入 Worker。
- GPU 委托能否在目标浏览器的 Worker 中稳定运行需要能力探测 → 已实现探测与 CPU 降级，并把实际委托方式如实回报到界面。

**推翻首选方案的条件**（尚未触发）：
调整机位与曝光后，MediaPipe 仍无法稳定跟踪持拍侧肩肘腕；或目标设备持续推理无法达到可用采样频率。
触发时先比较 rtmlib（读同一测试集），**不以更换更大的语言模型修复视觉输入失真**。

**日期**：2026-09-15

Sports2D 官方明确提示其二维角度依赖拍摄方向和运动平面，不能把斜侧拍摄的数值直接当成精确解剖角度。它也有误差，不作为真值。仅用于排查自研几何或绘图错误。

## D-005：契约先行，服务端不信任前端输入

**日期**：2026-09-15
**状态**：已实现

`packages/contracts` 是全链路唯一来源。API 收到证据包后用 `evidencePacketSchema.safeParse` 再次校验；模型输出一律经过 `validateModelOutput` 检查后才允许播报。

**为什么不能只靠提示词**：方案明确要求服务端实际检查 ID、schema、目标匹配和参考审核状态。实现中发现了一个真实的反例（见 D-007）。

## D-006：首版不引入向量检索与多 Agent

**日期**：2026-09-15
**状态**：已实现

- 知识按 `strokeType + focusId + cameraView` 直接选择。只有知识数量和检索复杂度确实增加时，再引入向量检索。
- 一组有效挥拍 → 构造证据包 → 选少量知识 → **一次**多模态调用 → 校验 → 展示。不引入多 Agent 编排、逐帧语言模型描述或多轮自我审查 —— 它们增加延迟，也不直接补足拍摄证据。
- 首版不自动重试模型超时，避免重复费用与陈旧播报。

## D-007：规则未审核时禁止输出达标结论（实现中发现的缺陷）

**日期**：2026-09-15
**状态**：已修复

**问题**：`evaluateRule` 的 `return_to_ready_zone` 分支在检查 `rule.status` **之前**就返回了 `target_met` / `suggest_adjustment`。结果是：一条 `status: "observation_only"` 且 `referenceId: null` 的规则，仍然会产出"本组约束达到"的判定。

**这直接违反了方案 8.4 的要求**：*"没有适用参考或规则未审核时，禁止输出技术动作'合格'"*。

**修复**：把审核状态检查提到数值判定之前。未审核或无参考时，只报告测量结果。

**教训**：安全约束必须写在代码路径的**前面**，不能依赖调用方记得检查。这条规则现在有 3 个测试用例守着。
