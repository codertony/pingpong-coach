用途：失败片段、分类、修复与回归结果。

**当前状态：尚无真实素材失败记录。** 下表记录的是开发过程中通过自动化测试发现的**代码缺陷**，
它们不能替代真实动作识别质量的验证。

## 失败分类口径

| 来源 | 排查方向 |
| --- | --- |
| 画面质量问题 | 拍摄要求与质量检查 |

## 已修复的代码缺陷

### F-001 · 分段状态机把间歇回踩误判为"稳定还原"

**日期**：2026-09-15
**分类**：分组错误（状态机与事件边界）
**严重度**：高 —— 直接产生虚假的"有效挥拍"，污染所有下游指标

**现象**：用户在准备区边缘来回小幅移动时，程序会把多次短暂进入累加成一个"稳定驻留"，从而错误地闭合一次挥拍。

**根因**：`zoneDwellMs` 只在"当前帧在区内"时累加，但从不因中途离开而清零。间歇性回踩被累加成了连续驻留。

**修复**：改为**连续驻留**判定 —— 只有当上一采样也在区内时才累加，中断即清零。同时把离开判定统一到 1.2 倍半径的有界滞后阈值。

**回归**：`segmentation.test.ts` 中「间歇性回踩准备区不会被累加成稳定驻留」守住此行为。

### F-002 · 规则未审核时仍会输出"达标"结论

**日期**：2026-09-15
**分类**：建议不适用（训练知识和适用条件）
**严重度**：高 —— 违反方案明确的安全约束

**现象**：`status: "observation_only"`、`referenceId: null` 的规则，仍然返回 `target_met`。用户会看到一个系统并**没有资格**给出的技术判定。

**根因**：`evaluateRule` 的 `return_to_ready_zone` 分支在检查 `rule.status` 之前就完成了数值比较并返回。

**修复**：把审核状态检查提前到数值判定之前。未审核或无参考时，只报告测量结果并说明原因。

**回归**：`rules.test.ts` 中「未审核规则只输出观察，不输出达标结论」等 3 个用例守住此行为，另有 `validate.test.ts` 在服务端二次拦截。

### F-003 · 单帧处理异常会中断整个采集循环

**日期**：2026-09-15
**分类**：调度（任务中断）
**严重度**：中 —— 一个坏帧会导致摄像头链路停摆

**现象**：`FrameScheduler` 的处理函数抛错时，异常从 `run()` 中逃逸成未处理的 Promise 拒绝。实测中 Vitest 直接报出 unhandled rejection。

**修复**：在 `run()` 内捕获异常，记录到 `lastError` / `errorCount` 后继续处理后续帧。位图释放逻辑移到 `finally`，保证异常路径也不泄漏。

**回归**：`scheduler.test.ts` 中「处理函数抛错也能释放位图并继续」。

### F-004 · 长宽比导致二维夹角严重失真

**日期**：2026-09-15
**分类**：指标错误（几何与坐标）
**严重度**：高 —— 肘角是本项目的核心测量之一

**现象**：1280×720 画面中真实的 60° 夹角，直接用 MediaPipe 输出的归一化坐标计算会得到约 72.0°，误差 12°，远超 10° 的验收门槛。

**修复**：`angleDegFromNormalized` 强制先按原图宽高还原像素坐标。Worker 适配层在产出关键点时就直接乘回宽高，避免下游误用归一化值。

**回归**：`geometry.test.ts` 中 6 个用例覆盖 45°/60°/135°/轴向直角/正方形画面/非法尺寸。

**遗留注意**：45° 与 90° 的测试数据曾两次写错（凑巧不失真），说明这个几何性质反直觉 —— 新增相关测试时必须先在像素空间构造真实角度，再转归一化，不要凭直觉手写归一化坐标。

### F-006 · 受限网络下无法取得 Pose Landmarker 模型，真实推理未经端到端验证

**日期**：2026-09-15
**分类**：姿态引擎或模型适配（**未验证**，非已修复）
**严重度**：高 —— 这是整条视觉链路唯一没有真机证据的环节
**状态**：**OPEN** —— 但已从"一次没跑过"收窄为"只剩你的机位没验"（见下方 2026-09-16 证据）

**现象**：构建沙箱对 `storage.googleapis.com` 不可达（该域名被解析到 `198.18.0.14`，TLS 握手直接 `SSL_ERROR_SYSCALL`）。
MediaPipe Pose Landmarker 的 `.task` 权重托管在此域名上，因此：

- `apps/web/public/models/pose_landmarker_full.task` 无法在沙箱内下载；
- 沙箱内**没有跑过一次真实的姿态推理**。

**沙箱内能验证的（已覆盖）**：客户端自身的协议与生命周期 ——
`init` 消息字段、GPU→CPU 降级是否如实上报、迟到/幽灵结果是否丢弃、
未就绪时位图是否释放、`dispose` 是否终止 Worker。
共 9 个用例，见 `apps/web/e2e/pose-engine.e2e.ts`。它们用**受控的假 Worker** 替换真实 Worker，
所以只证明"协议处理正确"，**不证明"模型输出正确"**。

**沙箱内不能验证的**：

- 模型权重能否加载；
- WebAssembly 运行时（`/wasm` 下的文件）是否与本机 Chrome 版本兼容；
- GPU 委托在你的显卡驱动上能否成功，失败时降级是否平滑；
- 真实画面下的关键点精度与抖动水平。

**本机验证步骤**：

```bash
# 1. 下载模型（约 9 MB）——沙箱做不了这一步
mkdir -p apps/web/public/models
curl -L -o apps/web/public/models/pose_landmarker_full.task \
  https://storage.googleapis.com/mediapipe-models/pose_landmarker/pose_landmarker_full/float16/latest/pose_landmarker_full.task

# 2. 复制 WASM 运行时（路径在 apps/web/node_modules 下 —— pnpm 把依赖装在声明它的包里，
#    根目录的 node_modules/@mediapipe 不存在；写错了会一个文件都复制不进去）
mkdir -p apps/web/public/wasm
cp apps/web/node_modules/@mediapipe/tasks-vision/wasm/* apps/web/public/wasm/

# 3. 启动并肉眼确认骨架贴合
pnpm --filter @pingpong/web dev
```

**判定标准**：站在镜头前，骨架应贴合关节；挥手时骨架跟随不脱节；
`/api/health` 与页面状态栏显示的委托方式应为 `GPU`（若为 `CPU`，需记录降级原因）。

**本机进展（2026-09-16，Windows 11 + Chrome）**：上面「沙箱内不能验证的」前两条已解决。

- 模型权重能加载（`pose_landmarker_full.task`，9.0 MiB，sha256 已回填 `models/manifest.json`）；
- `/wasm` 下的 WebAssembly 运行时与本机 Chrome 兼容；
- 实测：1280×720 输入下**委托方式为 GPU（未降级，初始化 174 ms）**，姿态处理 P95 约 9–11 ms，实测处理频率约 21 fps。

但这一步顺带暴露了两个此前完全未知的加载链路缺陷 —— **F-007** 与 **F-008**。在它们修掉之前，上面「本机验证步骤」的第 3 步跑不通，而且界面给出的失败原因还是误导性的。

**仍未验证（F-006 的核心）**：

- ~~**骨架是否贴合关节** —— 用假摄像头驱动时画面中无人，叠加层一次都没画过~~
  → **已在真实素材上做过一次，结论是贴合**（见下方"把骨架画在真实画面上"）。
  仍未验证的是**你自己的机位/身体/光照**；
- GPU 委托**失败**时的降级是否平滑 —— 本机 GPU 直接成功，降级路径只验证过"能连续实例化"，没经历过真实失败；
- 真实画面下的关键点精度与抖动水平。

**新增证据（2026-09-16）：解剖比例自检** —— 这是"骨架是否贴合"里**机器能查**的那一半。

用真实模型对真实视频的一帧跑姿态，把关键点按体尺度归一化后检查骨段比例：

| 指标 | 实测 | 人体参考 | 判读 |
| --- | --- | --- | --- |
| 前臂 / 上臂 | 0.51 / 0.581 = **0.878** | 0.85–0.95 | ✓ |
| 大腿 / 小腿 | 0.812 / 0.854 = **0.951** | 0.95–1.05 | ✓ |
| 左右上臂长度比 | **1.073** | ≈1（透视会让远侧略短） | ✓ |
| 左右大腿长度比 | **0.853** | 同上；该帧左腿确实更远 | ✓ |
| 肩宽 / 髋宽 | **1.96** | 1.4–2.0 | 偏上但合理 |
| 左踝 visibility | **0.394** | — | 该帧左踝确实快出画，**模型如实给了低置信度** |

**这批数字说明什么**：关键点落在**解剖学连贯**的位置上（错位或串部位的模型
不会给出这种自洽的比例），而且**置信度与遮挡一致**（看不全的点确实报低分）。

**这批数字不能说明什么**：**目视贴合仍然只有人能判断**。
比例自洽 ≠ 骨架画在关节上 —— 两者是独立的性质，前者是后者的必要条件而非充分条件。
**F-006 保持 OPEN。**

**回归**：`apps/web/e2e/pose-anatomy.e2e.ts`（需 `PPC_VERIFY_VIDEO` 指向真实素材，
缺失时 skip）。阈值取自上面这批实测值的宽松边界 —— 它挡的是"明显不像人"的输出，
**不是精度门槛**，样本量为 1 支视频。

**踩到的坑（值得记）**：第一版对**小腿**也做了左右对称断言，结果实测比值 **0.104**，
测试失败。但那不是代码错 —— 那帧左踝 `visibility` 只有 0.394，位置是模型**外推**出来的，
在不可靠的点上做几何断言本身就是错的。已改成**按置信度门控**：
两侧置信度都过阈值才断言，否则明确打出"因可见度不足未检查"，而不是静默跳过。

**新增证据（2026-09-16）：把骨架画在真实画面上，然后真的看了一眼**

比例自洽只是**必要**条件。为验充分性，把**产品自己的** `drawSkeleton`
画在真实视频的 7 个采样帧上、导出图片逐张看。
见 `apps/web/e2e/pose-overlay.e2e.ts`（需 `PPC_VERIFY_VIDEO`；图像写到
`PPC_OVERLAY_OUT` 指向的目录（不设置时写到 `apps/web` 下的临时输出目录，
已被 `.gitignore` 忽略），每帧一张全图 + 一张
持拍侧手臂局部放大图）。

| 项 | 实测 |
| --- | --- |
| 7 个采样帧的人体检出 | **7 / 7** 全部检出 |
| 叠加层是否真画出东西 | 7/7 都画出（6976 ~ 9398 个非透明像素）|
| 左右是否与画面一致 | 一致（`mirrored: false`，未被镜像）|
| 3s 帧（最低可见度 0.27）| 鼻尖落在鼻子上；**持拍侧（蓝）的肩→肘→腕整条链贴着右臂一直走到握拍手**；髋与腿的链条也贴住 |
| 6s 帧（最低可见度 0.89，最好的一帧）| 同上，且**持拍侧 = 人物自己的右侧**（面向镜头时它出现在画面左边）—— 左右标签正确 |
| 1s 帧（最低可见度 0.09，最差的一帧）| 侧面机位；**低置信度的琥珀色段落在真正被遮挡的远侧躯干上**，不是随机乱飘。持拍臂链条有约 20 ~ 30 px 偏移 |

**这批观察说明什么**：在**高置信度帧**上骨架确实画在关节上 —— 包括最关键的
那条"肩→肘→腕贴着持拍臂走到握拍手"。而且**低置信度与遮挡一致**
（看不清的远侧才发琥珀色），这正是期望的行为。

**这批观察不能说明什么**：

- 只有**一支素材、一个人、一个机位**（正面偏侧，约 2~3m）。换机位、换人未验；
- 判定者是**看图的多模态模型**，不是人。20 px 的偏差在 1280 宽的画面里只有
  1.5%，已经接近这种判读方式的分辨下限；
- 低置信度帧上确实看到了偏移，但**多少算"偏太多"要真人对着自己的机位判断**。

因此 **F-006 仍然 OPEN，但性质变了**：从"一次都没看过"变成
"在一支真实素材上确认贴合，仍缺你自己的机位/身体/光照"。
链路的"能不能跑通"已有证据；**"准不准"仍然一项目证据都没有**。

**回归**：`apps/web/e2e/pose-overlay.e2e.ts` 自动断言的是
"检出到了 + 叠加层不是空的"（后者顺带兜住"语义名与绘制代码脱节"）。
**它刻意不自动断言"画在关节上"** —— 那不是算术能判的，
写一条永远通过的断言等于自欺。

### F-007 · 模块 Worker 里加载不了 WASM 运行时，姿态引擎在本机完全起不来

**日期**：2026-09-16
**分类**：姿态引擎或模型适配（加载链路）
**严重度**：高 —— 本机首次跑真实推理时整条姿态链路根本没启动，且失败文案指向了无关原因
**状态**：已修复（加载链路）；识别质量仍见 F-006

**现象**：本机（Windows 11 + Chrome）跑 `pnpm --filter @pingpong/web dev`，点「开始训练」后界面毫无反应，一直停在「拍摄检查」页。界面给出的原因是"尚未加载模型…请先运行 `pnpm models:fetch`"，但模型早已下载并校验通过 —— **这条提示是错的，它掩盖了真正的失败**。真实错误只出现在浏览器控制台：

```
Failed to fetch dynamically imported module: /wasm//vision_wasm_internal.js?import
```

**根因**：两层叠加，第二层要修掉第一层才会暴露。

1. `MODEL_ASSET.wasmBasePath` 写成 `/wasm/`（带尾斜杠），MediaPipe 拼出的地址是 `/wasm//vision_wasm_internal.js`。更要命的是 **Vite dev 会把以 `/` 开头的动态 `import()` 改写成追加 `?import`**，而 `public/` 下的文件不允许被 import：单斜杠形式 Vite 直接返回 500，双斜杠形式不匹配 public 规则、命中 SPA 回退返回 `index.html`，浏览器按模块解析 HTML 失败。
2. 改用绝对 URL 后露出真问题：MediaPipe 的 WASM 加载器是 **UMD 经典脚本**，靠顶层 `var ModuleFactory` 落在**全局作用域**才能把工厂函数交出去，而它只会用 `<script>`（主线程）或 `importScripts`（经典 Worker）执行。本项目跑在**模块 Worker** 里（`new Worker(..., { type: "module" })`，为的是不让同步推理阻塞界面），`importScripts` 调用即抛 TypeError，MediaPipe 于是退回动态 `import()` —— 而 ESM 的 `var` 留在模块作用域，全局永远拿不到 `ModuleFactory`，抛 `ModuleFactory not set.`。

   还有一处必须一并考虑：**ESM 模块只求值一次**。GPU 创建失败降级到 CPU 时会二次 `createFromOptions`，此时模块已缓存不再执行 —— 即使第一次侥幸挂上了全局，第二次照样失败。这是实测确认的，不是推测。

**修复**：

- `apps/web/src/config/model-asset.ts`：`wasmBasePath` 改为带 origin 的绝对 URL、且不带尾斜杠。绝对 URL 不在 Vite 的改写范围内。
- `apps/web/src/vision/pose.worker.ts`：新增 `loadWasmFactory()`，在**每次** `createFromOptions` 之前自行抓取加载器源码，按经典脚本语义在全局作用域执行一遍，拿到 `ModuleFactory`。不能用动态 `import()` 代替（模块作用域 + 只求值一次）。

**回归**：`apps/web/e2e/app.e2e.ts` 中「点开始训练后：引擎真实就绪，练习页拿到实时画面」—— 真实浏览器 + 真实模型 + 假摄像头，断言能切到「练习」页、遥测出现实测处理频率（证明 `detectForVideo` 真的在跑，而不是只加载了模型就报 ready）。
**模型资产缺失时该用例 skip**，理由同 F-006：`storage.googleapis.com` 不可达，取不到 `.task`；已实测缺资产时 skip 而不是失败。

**遗留注意**：`(0, eval)` 需要页面 CSP 允许 `unsafe-eval`。dev 与 `vite preview` 都不下发 CSP，当前成立；**将来给前端加严格 CSP 时这里会静默失效**，必须换成别的加载途径（例如改回经典 Worker）。

### F-008 · 采集流从未接到界面上的 `<video>`，练习页只有黑屏

**日期**：2026-09-16
**分类**：工程（界面接线）
**严重度**：中 —— 推理、遥测、挥拍计数全部正常，但用户看不到任何画面，无法完成拍摄检查

**现象**：引擎就绪后点「开始训练」，能切到「练习」页，遥测有数字、挥拍计数在走，但实时画面区域全黑。

**根因**：`startCapture()` 内部的 `video` 是 `document.createElement("video")` 创建的**离屏**元素。`App.tsx` 的 `start()` 在 `setTab("practice")` **之前**执行 `if (videoRef.current) { … }`，而此刻界面还停在「拍摄检查」页，练习页的 `<video>` 尚未挂载 —— `videoRef.current` 是 `null`，赋值被静默跳过。等元素随后挂载时，已经没有任何代码再把流接上去。

**修复**：把挂流从 `start()` 中移出，改成 `useEffect`，依赖 `[tab, running, sourceKind]`，在元素真正挂载后接线；并加同源判断，避免切页时给导入视频重复赋 `src` 导致预览跳回开头。

**回归**：`apps/web/e2e/app.e2e.ts` 中同一个用例的画面断言 —— `<video>` 的 `srcObject` 是 `MediaStream`、视频轨道数为 1、`videoWidth > 0` 且未暂停。

### F-009 · 摄像头不可用：失败发生在引擎就绪之后，此前被 F-007 掩盖

**日期**：2026-09-16
**分类**：采集（设备可用性）
**严重度**：待定 —— 尚未确认是本机硬件/系统设置问题，还是代码问题
**状态**：**OPEN —— 设备枚举得到（5 个）但启动失败（Chrome 自身 10s 超时）。
已排除：被占用 / 系统隐私开关 / 权限设置 / 只是"慢"。等待用户重新插拔设备确认**

**现象**：修掉 F-007 之后首次真正走到采集这一步，界面报出：

> 未找到可用的摄像头设备
> 检查摄像头是否被其它程序占用，或改用导入视频。

**为什么现在才看到**：`start()` 的顺序是「先初始化引擎，再启动采集」，而引擎初始化失败时会直接 `return`，**`getUserMedia` 根本不会被调用**。所以在 F-007 修复前，这个错误被完全掩盖了 —— 它不是新引入的问题，是**新暴露**的问题。

**当初列的两种可能**（已被文末排查记录取代，保留以对照）：

1. 本机确实没有被浏览器枚举到的视频输入设备（无摄像头 / 驱动被禁用 / 系统隐私设置拦截）；
2. 设备存在，但 `getUserMedia` 的约束无法满足。

注意 `getUserMedia` 用的是**全 `ideal` 约束**（`ideal: 60/1280/720`），`ideal` 不会因为不满足而失败 —— 所以若确为设备存在的情况，就与约束无关，要另找原因。

**排查手段**：`capture-source.ts` 里已写好 `listCameras()`，但**目前没有任何地方调用它**，
「拍摄检查」页因而看不到"Chrome 到底枚举到了几个摄像头"。浏览器控制台一行即可判定：

```js
(await navigator.mediaDevices.enumerateDevices()).filter((d) => d.kind === "videoinput")
```

- 返回空数组 → 属于可能 1，是环境问题（Windows「隐私和安全性 → 相机」、设备管理器、是否被其它程序占用）；
- 返回非空但仍失败 → 属于可能 2，需要用返回的 `deviceId` 复现，那才是代码问题。

**界面改进（已实现）**：「拍摄检查 → 2 · 视频源」现在显示**浏览器当前枚举到的视频输入设备数量**、
**当前浏览器 UA**，以及**原始错误 `Name: message`**，并提供「重新枚举设备」/「授权并刷新设备名」两个按钮。

---

**排查记录（2026-09-16）** —— 结论：**不是占用问题，也不是系统隐私设置问题**。

已排除的（均为本机实测）：

| 假设 | 实测结果 |
| --- | --- |
| 摄像头被某进程占用 | FrameServer / FrameServerMonitor 均 `Stopped`；HKCU ConsentStore 下无任何 `StillInUse` 记录 ⇒ **没有任何进程持有摄像头** |
| 设备本身坏了 | 用应用**完全相同的约束**（`ideal 60/1280/720`）在真实 Chrome 上打开成功：`HIK 2K USB CAMERA`，1280×720@30 |
| Windows 隐私开关拦截 | 总开关 `HKLM\...\ConsentStore\webcam` = `Allow`；无企业策略（`Policies\Google\Chrome` 不存在） |
| 浏览器把该站点设成了 Block | Chrome 两个 profile、Edge 一个 profile 的 `Preferences` 里 `media_stream_camera` 例外**一条都没有** |

**当前最可能的解释**：页面不是在桌面版 Chrome / Edge 里打开的。本机注册的浏览器有
Chrome（默认）/ Edge / **夸克 Quark** / IE，且运行时**长期存在大量内置 WebView**：实测同期
`msedgewebview2` 37 个进程、`WeChatAppEx` 9 个进程。微信 / 钉钉 / IDE 预览面板这类内置浏览器
与网页视图往往**不暴露摄像头设备**，表现正是 0 个设备 + `NotFoundError`；这也与
「ConsentStore 里从来没有任何浏览器用过摄像头的记录」一致。

**下一步（待用户确认）**：在「拍摄检查」页读那行枚举数。若为 **0** 且 UA 不是桌面 Chrome / Edge，
即为此因；换桌面版 Chrome 打开 `http://localhost:5173` 验证。

**顺带发现（与摄像头无关，但会踩坑）**：该 dev server（`pnpm dev:all` 的 vite）不带 `--host`，

| --- | --- | --- | --- |

`HOST` 环境变量仍可覆盖；Playwright 通过命令行 `--host` 传入，优先级更高。

### F-010 · 预览镜像与骨架镜像不一致，骨架与人物左右相反

**日期**：2026-09-16
**分类**：工程（预览与叠加的一致性）
**严重度**：高 —— 骨架整体水平错位、与人物左右相反，软件在真机上无法用来确认机位；且直接违反红线 5 要保护的行为

**现象**：真机首次跑通后（F-006 的模型链路解锁），画面里人物正常，但骨架整体落在人物的一侧、与人物左右相反。用户的第一反应是"镜像反了"。

**根因**：**镜像只做了一半。**

- `skeleton-overlay.ts` 在绘制层按 `width - xPx` 做水平镜像，`App.tsx` 对摄像头传 `mirrored: true`；
- 但 `.stage video` **从来没有被镜像过** —— 全仓库搜不到任何 `transform`。

视频显示的是原始画面，叠加层用的却是镜像坐标 ⇒ 两者必然左右相反。这也解释了观感上像"骨架没贴合"：水平方向整体反向，纵向其实是对的。

**实测几何**（1280×720 窗口，stage 657.7×369.9）：

| 量 | 值 |
| --- | --- |
| stage / video / canvas 三者 rect | 完全一致 |
| 视频 intrinsic | 1280×720，与容器同为 16:9，`object-fit: contain` 不产生黑边 |
| 视频 computed transform（修复前） | `none` |
| canvas backing | 有检测时 `= imageWidth/Height`，同为 16:9 |

⇒ **不存在缩放或偏移问题，唯一的几何缺陷就是水平镜像。** 所以不要在这条上做尺寸相关的"修复"。

**修复**：`.stage video.mirrored { transform: scaleX(-1) }`，`PracticeView` 按 `sourceKind === "camera"` 加该类。导入视频不镜像 —— 那段素材不是自拍，绘制层对它同样不镜像。

**回归**：两侧分别钉住 ——
- `apps/web/e2e/app.e2e.ts` 断言摄像头预览的 computed transform 为 `matrix(-1,0,0,1,0,0)`；
- `apps/web/e2e/canvas.e2e.ts` 的「镜像只在绘制层生效」钉住绘制层自身的镜像行为。

**遗留注意（重要）**：这就是本 bug 的形状 —— **`mirrored` 必须在两侧取同一个表达式**。目前视频的 class 与 `drawSkeleton` 的选项都来自 `sourceKind === "camera"`，但二者是**两处独立求值**，改一处忘另一处就会原样复发。新增任何"预览上的叠加"（准备区、画框、标尺……）都必须同时考虑这一点。

顺带：`drawReadyZone()` **目前从未被调用**（与 `listCameras()` 是同类）。将来把它接上时，同样要遵守这条两侧一致的约束。

### F-011 · 视频循环播放后姿态推理静默失效，界面表现为"一直等待有效挥拍"

**日期**：2026-09-16
**分类**：姿态引擎或模型适配（时间戳契约）
**严重度**：高 —— 推理整条死掉，而界面只显示"等待有效挥拍"，没有任何报错

**现象**：导入一支 **8.13 秒、循环播放**的真实正手攻球视频后，练习页一直停在
"等待有效挥拍"。骨架在最初几秒正常，之后不再更新。界面遥测仍显示
`实测处理频率 30.0 fps`、`有效帧比例 92%` —— **这两个数字都来自调度器与质量评估，
不代表推理成功**，所以看起来一切正常。

浏览器控制台里是刷屏的 MediaPipe 计算图错误：

```
E0915 ... gl_graph_runner_internal_image.cc:68] Adding Image to stream image_in was not ok:
  INVALID_ARGUMENT: Packet timestamp mismatch on a calculator receiving from stream "norm_rect".
  Current minimum expected timestamp is 8100001 but received 0.
```

**根因**：`detectForVideo` 的 timestamp 必须**严格递增**。视频循环播放时媒体时间从
8133ms 跳回 0，MediaPipe 抛 `Packet timestamp mismatch` 之后**每一帧都继续失败**
（计算图已进入错误态），整条推理静默死掉。seek / 重播同理。

**为什么一直没被发现**：`app.e2e.ts` 用的是假摄像头，媒体时间单调递增，永远触发不到回绕；
而导入视频这条路径此前没有任何测试覆盖。

**修复**：`apps/web/src/vision/pose.worker.ts` 新增 `monotonicDetectTimestamp()`，
在**每次** `detectForVideo` 之前把媒体时间抬到"上一个 + 1ms"以保证严格递增。
只改传给引擎的时间戳，**不改**投影到 `PoseFrame` 的 `sourceTimeMs` ——
那是源视频的真实媒体时间，改了就破坏了它作为速度基准的含义。

**回归（实测，非推测）**：同一支视频，修复前控制台持续报 timestamp mismatch、
20 秒内只识别出 1 次有效挥拍；修复后错误消失，20 秒内识别出 **8 次**。

**教训（方法论）**：这条与 F-007/F-008 同类 —— 模块级测试全绿，整页串联 + 长时运行才暴露。
新增任何"按时间驱动"的引擎调用时，都要问一句：**时间戳回绕/seek 时会发生什么？**

### F-012 · 准备区写死在画面坐标，真实素材上导致一次挥拍都识别不出

**日期**：2026-09-16
**分类**：分组错误（状态机与事件边界）
**严重度**：高 —— 分段状态机一次都不触发，且**完全静默**

**现象**：修掉 F-011 后，同一支视频能识别出挥拍了，但数量明显偏少，
且大量时间停在"空闲（等待进入准备区）"。

**根因**：准备区中心是**写死的画面坐标**（水平中心、62% 高度），
`App.tsx` 在启动采集时无条件设置它。这个位置既不是用户手停的位置，
也不是任何用户相关的量；用户手停在别处时，状态机的
`distBodyScale <= readyZoneRadiusBodyScale` 永不成立，一次挥拍都不开启。
失败是**静默**的：没有报错、没有日志，界面只说"等待有效挥拍"。

**修复**：

1. **自动标定**：新增 `packages/motion-core/src/readiness.ts` 的
   `estimateReadyZoneFromDwell()`，从实际观察到的腕部位置估计准备区中心；
   `TrainingSession` 攒够 20 个腕部样本后自动标定一次。
2. **手动覆盖**：练习页提供「以当前腕部为准备区」「重标定准备区」两个按钮。
3. **如实标注**：界面明确写出"准备区由程序按腕部停留位置自动标定，不是既定参考"，
   用户随时可以覆盖 —— 不把程序猜的当成既定约束。
4. **让失败可见**：练习页显示当前分段阶段、`腕部距准备区 X 倍半径`、
   体尺度是否测到、持拍手腕是否检测到。这条最重要：**同一类失败以前是完全静默的**。

**估计器的选择（有实测对照）**：

第一版取「落点最密集的格子」。在真实视频上**选错了** —— 180 帧腕部样本里
最密集的格子只占 8%（15 帧），手腕几乎不停顿，于是被选中的是**引拍最高点**。

改为**局部速度加权**：挥拍时腕部速度高，准备与还原时低，只保留最慢的一半样本
再取中位数。同一支视频、同样 20 秒的对照：

| 准备区来源 | 20 秒内识别出的有效挥拍 |
| --- | --- |
| 落点最密集格子（第一版） | 1 |
| **速度加权（现行）** | **8** |

对照口径提醒：实验里"腕部样本中位数"作为对照时 20 秒 +0，但它是**接在速度加权

"中位数法无效"的证据。两个估计器最终都把准备区放进了腕部活动范围内

「快速扫过的轨迹不参与估计」「时间戳回绕不被当成高速」两条钉住这次的教训。

**仍未验证**：标定只在**一支**视频上做过对照，样本量为 1。
真实训练场景（有明确停顿、多种机位）下的表现**尚未验证** ——
不能由上面这张表推出"准备区标定已经好用"。

### F-013 · 视频导入时预览画面未镜像，骨架与人物左右相反

**日期**：2026-09-16
**分类**：工程（预览与叠加的一致性）
**严重度**：中 —— 与 F-010 同源，但方向相反

**现象**：截图显示导入视频时，**图片里的挥拍手臂在画面左侧、骨架的持拍链却在右侧**，
两者左右相反。

**根因**：`App.tsx` 里视频的镜像 class 用的是 `sourceKind === "camera"`，
而 `drawSkeleton` 的 `mirrored` 选项**同样**用这个表达式 —— 两处一致，
所以拍摄用摄像头时是对的（F-010 已修）。但**导入视频不镜像**这条规则本身是错的：
手机拍摄的视频**同样是自拍视角**，绘制层不镜像、预览也不镜像，两者虽然"一致"，
却与用户看到的人物真实左右相反。

**这正是 F-010 备注里警告的形状**：`mirrored` 必须在两侧取同一个表达式 ——
现在确实取了同一个，但**那个表达式的语义判断错了**。

**状态**：**已修复（2026-09-16）** —— 修法不是去猜素材来源，而是**把它做成用户选项**。

**修法**：「视频源」下新增「预览镜像」开关（只在导入视频时出现）：

- **镜像（手机自拍录制）** —— 默认值
- **不镜像（他人从对面拍摄）**

同时把 `mirrored` 收敛成**唯一的求值点**：`sourceKind === "camera" ? true : mirrorVideo`。
此前这个表达式在 `App.tsx` 里**各写了两遍**（视频的 class 与 `drawSkeleton` 的选项），
两处都错。现在只算一次，下面所有用到的地方都引用它。

**为什么做成开关而不是自动判断**：镜像只与**素材怎么拍的**有关，
自拍与他拍在像素上完全一样，程序分辨不出来。写死任何一边都会把另一半用错。
摄像头不走这个开关：自拍视角是它的固有性质，没有可选项。

**回归**：`apps/web/e2e/app.e2e.ts` 2 项。第一条读的是**实际计算样式**
（`getComputedStyle().transform`）而不是控件取值 —— 控件对了但样式没跟上，
恰恰是这个坑的形状；第二条断言开关只在「导入视频」下出现。

> 教训：F-010 与 F-013 是同一个坑的两半，两次都栽在"两侧各写一遍表达式"上。
> 收敛成唯一求值点之后，这类错误在结构上就不可能再出现。

### F-014 · 摄像头中途断开时界面继续假装在采集

**日期**：2026-09-16
**分类**：采集（设备可用性）
**严重度**：高 —— 界面**主动给出错误信息**，用户会一直干等一个不会再来的画面

**现象**（实测，不是推测）：训练进行中摄像头不可用后——

| 实际状态 | 界面显示 |
| --- | --- |
| 轨道 `readyState` = **`ended`** | 徽标 **"采集中"** |
| 视频停在最后一帧 | 状态栏 **"等待有效挥拍"** |

界面在这三点上都在撒谎：说还在采集、说在等挥拍、且**不给任何失败线索**。
用户唯一能做的事就是等。

**根因**：`startCapture()` 里的 `getUserMedia` catch 只覆盖**启动失败**；
设备在**中途**消失走的是另一条路，而当时没有任何代码监听它。
`capture-source.ts` 与 `App.tsx` 里都搜不到 `ended` / `readyState` 相关处理。

**修法**（两条路缺一不可）：

1. `capture-source.ts` 新增可选的 `onFault` 回调，并用**两条**检测途径：
   - 监听轨道的 `ended` / `mute` 事件；
   - **每 500ms 的存活探测**（读 `readyState`）。
2. `App.tsx` 收到故障后调 `stop("摄像头已断开，采集已停止")`，
   **复用完整收尾路径**（关轨道、终止 Worker、取消语音）—— 半停状态比不停更容易误导。

**为什么"只监听事件"不够（实测）**：`track.stop()` 会让 `readyState` 立刻变成
`ended`，却**不派发任何事件**（`ended`/`mute` 计数都是 0）。真实拔设备时浏览器
是否派发取决于实现 —— 光靠事件会漏。

**为什么用 `stop(message)` 而不是 `stop()`**：`stop()` 会把状态栏设成"已停止"，
而这行是练习页**唯一**能看到的解释。第一版就是只改了徽标和"拍摄检查"页的错误框，
练习页仍然没有任何提示 —— 被回归用例当场抓住（用例里那条断言就是为此加的）。

**顺带修掉的一个陷阱**：`stop` 加了可选 `message` 参数后，直接 `onClick={onStop}`
会让 React 把 **MouseEvent** 当 message 传进去，状态栏显示 `[object Object]`。
绑定处改成 `onClick={() => props.onStop()}`，并在用例里断言不出现 `[object`。

**回归**：`apps/web/e2e/camera-fault.e2e.ts` 2 项：
- 轨道消失后徽标变"已停止"**且**状态栏出现"摄像头已断开"；
- 用户主动停止**不会**误报成设备断开（防止 `stop()` 自己的 ended 触发故障）。

### F-015 · 界面上的"姿态处理 P95"不是用户感受到的那段延迟

**日期**：2026-09-16
**分类**：指标错误（口径）
**严重度**：中 —— 数字本身是真的，但**标签与它测量的东西不符**，会系统性低估延迟

**现象**：练习页显示"姿态处理 P95"，数据源是 `result.inferenceMs` ——
那是**Worker 内部的推理耗时**。它不包含：

- 帧调度器的排队时间（繁忙时帧会被替换、要等当前帧处理完）；
- 主线程 ↔ Worker 的跨线程传输与序列化。

而这两段恰恰是**最容易出问题**的部分。结果就是：界面上的数字看起来很健康
（实测 9–11 ms），但用户真正感受到的延迟没有被测量，也没有被显示。

**根因**：`PoseResult` 里同时有 `receivedAtMonoMs`（浏览器收到帧）、
`inferredAtMonoMs`（推理完成）、`inferenceMs`（推理本身），
而遥测取错了字段 —— 拿了最窄的那个。

**为什么这比"数字算错"更值得记**：数字没有错，是**标签错了**。
这类偏差不会让任何测试失败，也不会让人察觉，只会让所有关于性能的讨论
建立在一个偏小几个数量级的读数上。

**修法**：拆成两个口径，`TrainingTelemetry` 里分别统计、界面上分别显示：

| 字段 | 含义 |
| --- | --- |
| `poseLatencyP95Ms` | **端到端处理延迟**：收到帧 → 骨架可用，含排队与跨线程。这是用户感受到的那段 |
| `poseInferenceP95Ms` | Worker 内推理本身。与上面的差值 = 排队 + 跨线程 + 序列化开销 |

界面标签也改了："端到端处理延迟 P95" / "其中推理耗时 P95"，并带 `title` 说明口径。

**顺带修掉**：`dispose()` 原先不清延迟样本数组（`poseLatencies` 累积到 500 条），
会话结束仍挂在对象上。现在两个延迟数组都清。

**仍未测的**：采集段延迟（摄像头曝光 → 浏览器收到）。那需要真机摄像头，
不在代码可测范围内 —— **不要**把 `poseLatencyP95Ms` 当成完整的端到端延迟。

**回归**：`apps/web/test/telemetry.test.ts` 4 项，其中一条专门断言
"端到端必须显著大于推理本身"，另一条断言两者各自独立统计、不互相污染。

### F-016 · 用户选了"肘角伸展模式"，产品静默不算对应指标

**日期**：2026-09-16
**分类**：建议不适用（训练知识覆盖面）
**严重度**：中 —— 产品**静默忽略用户的选择**，还把反馈的 focusId 标成用户选的那个

**现象**：界面「本组关注点」里，「肘角伸展模式」与「肘相对躯干移动」是**可选**的。
选它们之后：

- 证据包里的 `focusId` 标着用户选的那个（模型被框在这个关注点上）；
- 但**对应的肘角指标根本没被算出来** —— `computeElbowAngleAtForwardPeak`
  定义了、导出了，**从未被任何产品代码调用**；
- 本地规则也只有 `return_to_ready_zone` 一条，所以另外两个选项走到
  "规则未覆盖"分支，界面那条提示只说"其它关注点当前只输出观察"，
  **没告诉用户"你这个选择没有被测量"**。

**怎么发现的**：做"哪些已完成的导出其实没接进产品"的审计时，
把 motion-core 的公开符号逐个在 `apps/` 里搜，`extractHandGeometry` 与
`computeElbowAngleAtForwardPeak` 都是**零调用**。前者是已知的能力边界，
后者对应着一个**用户可选**的关注点 —— 那才是缺陷。

**顺带发现命名不诚实**：`elbow_angle_at_forward_peak_deg` 这个名字声称
"向前挥拍峰值"，但契约里 `StrokeEvent` **没有**这个时刻（只有
`startMs` / `endMs` / `anchor`），而且原实现取的是**整组区间的中位数**。
两层都不诚实。

**修法**：

1. 特征改名为 `elbow_angle_at_wrist_peak_deg` —— 锚点确实存在，
   名字与锚点对齐（与 `return_after_wrist_peak_ms` 不叫
   `recovery_after_impact_ms` 是同一条纪律）。
2. 重写计算：取**锚点前后 ±80ms 窗口内**的肘角中位数。
   窗口必须锚在真实事件上 —— 退化成"整区间中位数"就等于声称一个
   没在锚点处测到的量。窗口内没采到就报**缺失 + 原因**，不拿窗口外的帧冒充。
3. 会话里**按关注点**计算：选「肘角伸展模式」时才推入这个特征。

**回归**：`motion-core/test/features.test.ts` 5 项。关键一条是
"只取锚点附近窗口内的采样，远处的值不得混入" —— 它同时断言结果**不等于**
整区间中位数，挡住回到旧语义的退化。

**同一缺陷的第二层：mock 适配器答非所问**（同一次审计顺带发现）

`mockCall` 写死只找 `return_after_wrist_peak_ms`，**完全忽略 `packet.focusId`**。
用户选「肘角伸展模式」时，mock 返回的观察文本仍在讲返回准备区时间。

叠加上面第一层（本地规则也只看 `return_to_ready_zone`），真实后果是：
那条路径下用户几乎拿不到任何与**所选关注点**相关的反馈。

已修：mock 按 `focusId` 挑主测量并复述**程序已算出的**值；对应测量缺失时
如实说明原因、不编造数值。回归 `provider.test.ts` 5 项，其中一条专门断言
"关注点是肘角时，观察文本**不得**出现『准备区』"。

**仍未做的（如实记录）**：这两个关注点**仍然没有规则**，所以只会输出
观察、不做达标判断。这是刻意的（红线 4：规则未审核不得给结论），
不是遗漏。界面提示已改为如实说明"会把对应测量算出来交给模型印证，
但不做达标判断"。

### F-017 · 模型 id 可由环境变量覆盖，加载路径却写死 —— 会伪造溯源

**日期**：2026-09-16
**分类**：工程（模型资产一致性）
**严重度**：中 —— 不会崩，但**上报的 modelId 与实际加载的权重可能不一致**

**现象**：`model-asset.ts` 里

- `modelId` 取 `import.meta.env.VITE_MODEL_ID_ASSET ?? "pose_landmarker_full"`
- `modelAssetPath` **硬编码** `"/models/pose_landmarker_full.task"`

这个环境变量的用途是在**同一素材**上比较 full 与 lite
（见 `models/manifest.json` 里 lite 的 `role: speed-comparison`）。
但设了它只会改 id、**不改加载路径** —— 于是会**加载 full 权重、却上报 lite 的 modelId**。

**为什么这比读错一个数字严重**：`modelId` 是写进 `PoseFrame`、
用于**评估与费用归因**的。对不上等于伪造溯源 —— 而本项目对"如实标注"的要求
（红线 10 的 mock 标记、F-014 的界面不撒谎）都是同一个原则。

**怎么发现的**：接着做"机械可查的重复真相源"审计时，顺着刚加的
`check:docs`（文档一致性）思路去查**代码内部**的一致性 ——
manifest 声明了 `modelId ↔ path` 的对应，而代码里这两件事各写各的。

**修法**：路径**由 id 推导**（`POSE_MODEL_PATHS` 映射表），
且未知 id **当场抛错**而不是静默退回默认模型 —— 静默退回同样会造成
"上报 id ≠ 实际权重"。

**回归**：`apps/web/test/model-asset.test.ts` 4 项，断言
① manifest 每个 modelId 都声明了路径；② 前端映射表的 id↔路径与 manifest 一致；
③ 路径必须来自映射表（不是写死）；④ 未知 id 会明确抛错。

### F-020 · 手部点与腕部锚点不在同一坐标空间，每一只手都被静默丢弃

**症状**：手部模型加载成功、也**确实检出了手**（`handDetected: true`），
但关键点里手部 21 点**永远是缺失**。手指几何永远算不出、绘制永远不画。

**根因是单位口径**。`apps/web/src/vision/pose.worker.ts` 的 `projectHands`
把两份**不同空间**的数据交给 `assignHandsToSides` 比距离：

| 数据 | 实际坐标空间 |
| --- | --- |
| MediaPipe 手部 `landmarks` | **归一化**（0..1） |
| 姿态腕部锚点（`toWrist` 乘过宽高） | **像素**（0..1280） |

距离于是恒为数百像素，远超容差 `hypot(W,H)*0.15 ≈ 220`，
**每一只手、每一帧**都被判成"超出容差"。
`assignHandsToSides` 自身没问题 —— 它的文档写明"归一化或像素均可，
**只要与 anchors 同一空间**"，是**调用方**违反了这条约定。

**为什么静默**（这一条比缺陷本身更值得记）：

- `handDetected` 取自 `hands.length > 0`，仍然为 `true` —— **遥测说"检出了手"**；
- 手部点被那段注释写着"显式记为缺失，而不是悄悄不产出"的代码如实写成缺失
  —— 于是从外部看，**一切都像在按设计工作**。

**实测（同一帧真实数据的 A/B；素材 1280×720，容差 220 px）**：

| 口径 | 成功分配的帧数 |
| --- | --- |
| 产品当时的口径（归一化点 vs 像素锚点） | **0 / 31** |
| 把同一批点换算成像素后再分配 | **2 / 31** |
| 被丢弃时的距离 | 625 ~ 712 px（超容差约 3 倍） |

**修法**：在 `projectHands` 里**先统一换算到像素**再比距离；
另加 `pixelToKeypoint`，把"这里拿到的已经是像素、不能再乘一次宽高"写成代码。

**回归**：`apps/web/e2e/hand-on-footage.e2e.ts` 两条 ——
① 上面那张 A/B 对照表本身；② 走**真实 Worker** 的端到端断言
（检出手的帧里，手部点必须是有效坐标）。
两条都验证过"把修复回退即变红"。

**教训**：这个缺陷**任何单元测试都抓不到** —— `assignHandsToSides` 的单测全绿，
因为它自己是对的。只有走真实 Worker 才碰得到那一行。

### F-021 · 手部叠加有两个各自独立、又都静默的绘制缺陷，手指从来没画出来过

**症状**：F-020 修好（手部点真的有了有效坐标）之后，画面上**仍然看不到手指**。
把 Worker 吐出的 `keypoints2D` 交给产品绘制层再放大看，看到的**是一团白点**。

**① 名字拼错 —— `drawHand` 一次都没执行过**

`drawHand` 按 `${侧}_hand_${后缀}` 拼名字查点。但契约里**只有腕点**带
`_hand_` 中缀：

| 契约里的名字 | 拼出来去查的名字 | |
| --- | --- | --- |
| `right_hand_wrist` | `right_hand_wrist` | ✅ |
| `right_index_mcp` | `right_hand_index_mcp` | ❌ 不存在 |

21 个点里 20 个查不到，`drawHand` 的三锚点守卫（腕 / 食指根 / 小指根）
直接 `return` —— **手部从来没有被画出来过**。

**② 通用关键点循环又把手部点当姿态点画了一遍**

`drawSkeleton` 的关键点循环对**所有**关键点生效，手部点于是按持拍侧
姿态点的尺寸绘制（半径 `width/170 = 7.5 px`）。而手在这段素材里只有约
**91 px** 宽（实测包围盒对角线），**点比指间距还大** —— 21 个点糊成一团白，
`drawHand` 那套细点细线完全被盖掉。
（这一条在 F-020 修好之前不会显现：那时手部点是 NaN，压根不画。）

**为什么测试没抓住 —— 测试与实现"错得一模一样"**

`apps/web/e2e/canvas.e2e.ts` 的 `rightHandPoints()` 用的是
`right_hand_index_mcp` 这类**契约里根本不存在**的名字 —— 与当时 `drawHand`
的错法**完全一致**。于是那组测试一直在量**通用循环画出来的像素**，
却报成"手部绘制通过"。**测试与被测代码共用一个错误假设，是最难发现的形态。**

**修法**：

- `drawHand` 不再拼名字：按侧切片契约的 `HAND_LANDMARK_NAMES`，
  骨段改用**下标**（`HAND_LANDMARK_INDEX`）而不是名字 —— 下标不会拼错。
- 关键点循环**跳过手部点**（`HAND_KEYPOINT_NAMES`），手部只由 `drawHand` 画。
- `canvas.e2e.ts` 的 `rightHandPoints()` 改用契约名 —— 那一条测试从此
  **真的**执行 `drawHand`（验证过：回退名字修复，它立刻变红）。
- 新增 `apps/web/e2e/skeleton-overlay.e2e.ts` **3 条，不需要任何素材、
  CI 上就会跑**：
  ① 只给手部 21 点 → 必须画出 > 200 像素（抓"名字查不到"）；
  ② 只给一个非锚点手部点 → 必须 **0** 像素（抓"通用循环重复画"）；
  ③ 阴性对照：只给姿态点 → 必须 > 0（跳过逻辑不得误伤）。

### F-022 · 连续对拉时相邻几板被合并成一次挥拍（少算）

**日期**：2026-09-16
**分类**：分段（阈值校准）
**严重度**：高 —— 挥拍数直接决定"本组 3 次"这类计数，少算会让用户以为自己的板数不对；
且它会让**下游的组特征**（组内一致性、返回准备区时间）建立在错误的样本划分上
**状态**：**OPEN —— 已量化到"1 次 vs 三遍循环"，但改阈值前必须先有人工标注**

> **更正（同日，见 F-025）**：本节原先把"整段只检出 1 次挥拍"主要归因于
> **相邻几板被合并**。F-025 找到之后才知道，那个 1 次**主要是另一个更严重的缺陷造成的**
> —— 超时判定用了切换前的旧起始时刻，导致会话跑过 3 秒后**每一笔新挥拍都被当场丢弃**。
> 修掉 F-025 后，同一段真实素材从 **1 次变成 2 次**。
>
> **合并现象本身仍然成立**（相位日志里那三遍 `backswing→forward→returning`
> 确实发生在一条 StrokeEvent 内部），但在 F-025 修好之前，
> **它是次要原因，不是主因**。把主因归错会把人引向错误的修法（去调阈值），
> 所以这条更正必须留着。
>
> 现在的真实情况是：**两个问题都在**。修掉 F-025 后真实素材检出 2 次，
> 而肉眼可见的挥拍明显更多 —— 剩下那部分才是本节要解决的合并问题，
> 它仍需要人工标注才能定量。

**怎么发现的**：接 `eval:replay` 的观测导出（`e2e/segmentation-eval.e2e.ts`），
用**产品真实的 `TrainingSession`** 逐帧跑完整段素材（1280×720、8.15s、244 帧、30fps）。

**现象**：整段只闭合了 **1 次**挥拍（窗口 1267 ~ 3167 ms），
而逐帧相位日志显示，**在这一条 StrokeEvent 内部**：

```
ready@833 → backswing@1333 → forward@1733 → returning@1867
          → backswing@1933 → forward@2067 → returning@2367
          → backswing@2500 → forward@2833 → returning@3033 → ready@3167
```

`backswing→forward→returning` 循环了**三遍**才回到 `ready`。
之后（3.3s 起）相位在 `idle ↔ ready` 之间反复横跳，**再没进过 backswing**。
结束原因是 `stroke_too_long`。

**根因（推测，需标注确认）**：`returnStableMinMs = 120` 要求"回到准备区并稳定驻留 120ms"
才算一板结束。而真实连续对拉里，两次挥拍之间**手并没有回到准备区停留** ——
日志里 `returning@1867 → backswing@1933` 只隔了 **66ms**。
于是状态机把三遍挥拍当成"一次过长的挥拍"。
阈值本身是**暂定值**，从未在真实素材上校准过（见 `configs/thresholds.json`）。

**为什么没有更早发现**：这套阈值只在 `motion-core` 的单测里跑过，
而那些测试喂的是**构造数据** —— 构造数据里每板之间必然有稳定的准备区驻留，
正好绕开了这个真实素材才有的形态。这与 F-020/F-021 同属一类：
**测试全绿只说明被测的那个场景成立**。

**为什么现在不改**：改阈值需要先知道**改好还是改坏**，那需要真值。
没有标注时调参只是把猜测从一个值挪到另一个值（README 第 9 节的明确纪律）。
评估流水线已经接通，缺的只是**人工标注**这一步：

```bash
# 1. 导出观测与联系表
PPC_VERIFY_VIDEO=<素材路径> pnpm --filter @pingpong/web test:e2e segmentation-eval
# 2. 照着 contact-sheet.png 标真值，写进 evaluation/samples.json 的 annotation.strokes
# 3. 出指标
pnpm eval:replay --manifest evaluation/samples.json
```

**样本量的诚实交代**：以上是**一支素材、一个人、一个机位**。
"连续对拉会合并"这个形态在这段素材上是**直接可见**的（相位日志就是证据），
但"合并发生的频率有多高"需要多段素材 + 标注才能回答。

**回归**：`e2e/segmentation-eval.e2e.ts` 断言"整段素材必须至少检出一次挥拍" ——
它挡的是"分段链路在真实数据上完全不动"这类彻底失效。
**它刻意不断言具体检出次数** —— 那正是 F-022 要测的量，钉一个当前值只会
把缺陷固化成"预期行为"。

### F-022 补测 · 用**合成数据**把合并机制量化到可操作

**能这么做的前提**：`AGENTS.md` 的分工是"合成样本适合验证计算与程序边界；
真实动作识别质量必须用真人标注数据验证"。下面严格待在允许的那一半里 ——
它**不声称任何识别准确率**，只回答"门槛与合并的因果关系"这个确定的问题。

合成依据**照抄实测值**，不是随手编的：回位在区内停留 D 毫秒（实测落在 33/67/100/166ms）、
回位落点 0.29~0.40 体尺度（实测）、峰值 0.45 体尺度、40ms 采样步长（30fps）。
代码：`packages/motion-core/test/segmentation-merge.test.ts`（3 项，已知真值 = 每循环一板）。

**结果 1 · 合并的交叉点在 200ms，而不是名义上的 120ms**

| 回位驻留 | 0 | 20 | 40 | 60 | 80 | 100 | 120 | 160 | 200 | 240 ms |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 检出板数（真值 10）| 5 | 5 | 5 | 5 | 5 | 5 | 5 | 5 | **9** | **9** |

即：**十板被稳定地压成五笔（两板并一笔），直到驻留达到约 200ms 才逐板分开。**
产品配置写的是 `returnStableMinMs = 120`，但**实际需要约 200ms 的墙上时间** ——
因为驻留计时是从"进入区内的**下一帧**"才开始累计的（进入那一帧会把 `zoneDwellMs` 清零），
每板白吃一帧 ≈ 40ms，而且必须**连续**在区内。

**结果 2 · 落点在区外时不是"少检"，是"整体静默"**

| 回位落点 | 0.15（区内，半径 0.30）| 0.35（区外）|
| --- | --- | --- |
| 检出板数（真值 10）| **9** | **0** |

落点在区外 → 腕部从不进入准备区 → `beginStroke` 永远不开头 → **一板都检不出**。
**这是这条缺陷最致命的地方**：半径只要比实际回位距离小一点点，产品就从
"数得少"直接掉到"完全不工作"，而中间没有过渡。

**结果 3 · 合并只会少算，不会多算** —— 用四组参数交叉验证过
（驻留 0/60/120/240ms × 落点 0.15/0.35），检出板数**从不大于**真值。
所以它不会退化出 F-001 那种虚假挥拍。

**把这三条与真实素材的实测拼起来**，F-022 的成因就完全清楚了：

> 真人连续对拉时，腕部的回位距离是 **0.29~0.40**，正压在半径 **0.30** 上 ——
> 一半的板进区、一半不进；进区的那几帧也只停 **33~67ms**，
> 离实际需要的 ~200ms 差得远。于是 8.15s 里只闭合了 2 次。

**独立视觉复核（2026-09-17）**：上面整条论证此前都建立在**算法自己的通路**上
（合成数据 + 腕部信号）。这一轮把它单独复核了一遍 —— 把素材导成 **0.1 秒一格**的
联系表（82 格）**逐格看完**：肉眼可见是**连续对拉**，挥拍数量级 **8~11 次**，
而检测报了 **2 次**（1900ms / 2200ms 两段）⇒ **"相邻几板被合并"成立，且差距一个数量级**，
这次**不依赖算法自身的信号**。
（**没有**据此发布 precision/recall：从 0.1 秒格子判断"这一板从哪开始"的不确定度
约 ±200~300ms，正压在 800ms 单板所需的 ±200ms 上 —— 那样报出来的数主要反映读图误差。
详见 `docs/evaluation-log.md` 事实 8。）

**可操作的建议（有证据支撑，但最终取值仍需标注）**：

1. **先校准准备区半径**。它是决定"能工作 / 完全不工作"的那个开关，
   而实测回位距离正压在边界上 —— 这是投入产出最高的一处。
2. **再校准回位驻留要求**。名义值 120ms ≠ 实际值 ~200ms，这中间的差
   应当写进 `configs/thresholds.json` 的说明，否则调参的人会按名义值推理。

**仍然不能由这条推出的**：半径到底该调到多少。合成数据里的"回位距离"
是我按实测分布填进去的，而真实回位的**分布形状**（集中还是分散、是否随体力漂移）
需要真人素材才能得到 —— 那正是 `annotation.strokes` 那一步要说的事。

### F-024 · 端到端延迟遥测把 **Worker 时钟**与**主线程时钟**相减，算出负延迟

**日期**：2026-09-16
**分类**：遥测口径（跨线程时钟）
**严重度**：高 —— 界面状态栏显示的"姿态处理 P95"是用户唯一能看到的延迟数字，
而它被系统性低估；F-015 刚把它的口径拆对，这里又发现**拆开的两个数是不同源的**
**状态**：**已修复**（`PoseEngine` 改为在主线程重新盖章）

**怎么发现的**：写 20 分钟稳定性测试时顺手自己量了一遍引擎往返延迟
（乐观地按 `frameId` 记下提交时刻，结果回来时再取一次 `performance.now()`），
得到 **中位 16.3ms**；而同一个进程里、同一批帧，会话遥测报的是 **0**。
两个数对不上，于是把**两个口径并排量了一次**：

| 口径 | min | 中位 | p95 | max |
| --- | --- | --- | --- | --- |
| 自测（主线程两端相减，正确） | 8.5 | **16.3** | 1037.6 | 3417.3 ms |
| 会话遥测口径（Worker 时钟 − 主线程时钟） | **−163.2** | **−155.4** | 865.9 | 3245.6 ms |

**根因**：`pose.worker.ts` 里

```ts
inferredAtMonoMs: performance.now(),   // ← Worker 自己的时钟
```

而 `TrainingSession` 拿它去减主线程盖的 `receivedAtMonoMs`：

```ts
this.poseLatencies.push(result.inferredAtMonoMs - result.receivedAtMonoMs);
```

**两个时刻必须同源**才能相减。实测这套浏览器/Worker 组合下两者基线差约 **155ms**，
于是绝大多数样本变成负数，P95 被推到 0 附近。
（`PoseEngine` 中间只是把消息 `...msg` 摊开透传，没有重新盖章。）

**为什么既有测试抓不到**：`apps/web/test/telemetry.test.ts` 的 4 项测试
**用同一只时钟构造** `receivedAtMonoMs` 与 `inferredAtMonoMs`，
于是"两个时钟不同源"这个前提在测试里**从来不成立**。
这与 F-020（测试与被测代码共用同一个错误假设）、F-021（测试在量错的东西）、
F-023（门禁在扫错的目录）是**同一个形态**：验证没有落在要验证的对象上。

**修法**：`PoseEngine` 在主线程收到结果时**重新盖章**：

- `inferredAtMonoMs` = 主线程 `performance.now()`（延迟就用它算）；
- Worker 报的原值保留在新增的 `workerInferredAtMonoMs`（只作诊断核对）。

这样契约里那句"收到帧 → 骨架可用"才真的成立。修完两个口径完全一致
（6.3 / 24.4 / 901.3 / 3285.0 ms），界面上的 P95 从 **0** 变成 **25.9 ms**。

**顺带更正一处陈旧注释**：`PoseResult.inferenceMs` 上写着"姿态处理耗时：收到帧 → 骨架结果可用"，
但它的值其实是 **Worker 内部**的推理耗时，不含排队与跨线程 ——
那条注释与 F-015 拆开的口径自相矛盾，已改成准确说法。

**回归**：`apps/web/e2e/pose-engine.e2e.ts` 新增一项，用**受控的假 Worker**
故意报一个完全不同时钟下的时刻（`10^7`），断言 ① 交出的 `inferredAtMonoMs`
落在主线程的 `[提交时刻, 现在]` 区间内；② `workerInferredAtMonoMs` 保留原值。
已验证**回退修复后该项立刻变红**。

**方法论**：这个缺陷是"顺手多量一个数"发现的 —— 我本来只是在写稳定性测试，
多记了一个延迟分布，结果发现它与产品遥测对不上。
**如果一个测试只复述被测代码的假设，它证明不了那个假设。**

### F-025 · **会话跑过 3 秒之后，再也记不到任何挥拍**（超时判定用了切换前的旧起始时刻）

**日期**：2026-09-16
**分类**：分段（状态机）
**严重度**：**致命** —— 产品的核心功能是"一组 3 次挥拍"，而它在**第 3 秒之后完全停止计数**。
用户看到的现象就是最初报的那个："一直在等待有效挥拍"
**状态**：**已修复**

**现象**：连喂 30 轮**完全相同、且已验证可用**的挥拍（600 帧），只出 **4 次挥拍 / 1 组**；
此后无论怎么挥都不再计数。逐帧相位日志显示：第 4 笔之后每一轮都报
`本次挥拍不完整（stroke_too_long）`，而腕部明明就在准备区里（`腕部距准备区 0.06`）。

**根因（三行之内）**：`StrokeSegmenter.push` 里，超时判定用的是一个
**在状态机切换之前**算好的 `elapsedInStroke`，却在切换**之后**才拿它去比：

```ts
// 切换之前：
const elapsedInStroke = sample.sourceTimeMs - this.strokeStartMs;

switch (this.phase) {
  case "ready":
    ...
    if (zoneDwellMs >= readyStableMinMs && this.currentStrokeId == null) {
      this.beginStroke(sample);   // ← 这里把 strokeStartMs 设成本帧时间
    }
}

// 切换之后：
if (this.currentStrokeId != null && elapsedInStroke > this.config.maxStrokeDurationMs) {
  return this.abortCurrent("stroke_too_long");
}
```

于是**本帧刚刚开启的那一笔挥拍**，会被拿去减**上一笔**清算后的 `strokeStartMs` ——
而 `cleanupStroke()` 把它清零了，所以：

```
elapsedInStroke = sourceTimeMs − 0 = sourceTimeMs
```

一旦会话跑过 `maxStrokeDurationMs`（默认 **3000ms**），
`sourceTimeMs > 3000` 恒成立 → **每一笔新挥拍都在开启的那一帧被判超时、当场丢弃**。
表现就是"前 3 秒正常，之后永远静止"。

**为什么所有测试都放过了它**：既有分段用例都只喂**一到两笔**挥拍，
时间跨度不到 3 秒 —— **恰好绕开了触发条件**。
这跟 F-020/F-021/F-023/F-024 是同一个形态：验证没有落在会出问题的那个输入区间上。

**修法**：把 `elapsedInStroke` 移到底部**当场算**，保证用的是本次 push 之后的
`currentStrokeId` / `strokeStartMs` 这一对**同一时刻**的状态。
（混用"切换前"和"切换后"的状态，是这类状态机的典型陷阱。）

**顺手排查了同类**：`push` 在 switch **之后**还会用到 `speed` 与 `distBodyScale`，
但它们描述的是**当前这一帧的输入**、不是会被 switch 改写的状态，
所以那样用是对的。该函数里只有超时判定这一处混用了前后状态。

**实测修复效果**：

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| 连喂 30 轮合成挥拍（`strokesPerGroup=3`） | 4 次挥拍 / **1 组** | **30 次挥拍 / 10 组** |
| 同一批数据但不成组（`strokesPerGroup=99`） | 4 次 | **30 次** |
| **真实素材**（8.15s，逐帧 244 帧） | **1 次** | **2 次** |

第三行的对比同时说明两件事：① F-025 确实在真实数据上卡死了计数；
② 但真实素材仍然**远低于肉眼可见的挥拍数**，那是**另一件事**（见 F-022 的更正）。

**回归**：
- `packages/motion-core/test/segmentation.test.ts`：连喂 8 笔、断言时间基线越过 3 秒后
  仍至少有 6 笔闭合。已验证**复现原缺陷后立刻变红**（8 → 5）。
- `apps/web/test/session-groups.test.ts`：连喂 30 轮、断言 ≥20 笔 / ≥5 组。
  这也是**第一份跑过第二个组**的测试（此前 `telemetry.test.ts` 特意把
  `strokesPerGroup` 设成 99 以避开成组，夹具的 `runSyntheticGroup` 拿到第一个包就 break）。

**方法论**：这个缺陷是被**20 分钟稳定性测试**逼出来的 —— 我本来只是想验证
"跑久了会不会泄漏"，结果发现"跑久了根本不工作"。
**长时运行的测试不只测稳定性，它会把只在时间轴后段才出现的状态机缺陷一起抖出来。**

**日期**：2026-09-16

唯一的兜底是 API 侧那 2 MiB 的 `maxRequestBytes`，而它是**拒绝**而不是**降采样**。
所以理论上会出现"请求被拒"而不是"载荷变小"。

1. **能校的**：`quality` 块补上**双向**校验（每个值两边一致 + JSON 不许多出代码没有的键）。

   和 `quality` / `segmentation` 一样有测试守着。
3. 文件顶部的 `$runtimeNotice` 改为列出**三处**代码真值
   （`DEFAULT_THRESHOLDS` / `DEFAULT_SEGMENTATION` / `DEFAULT_QUALITY_CONFIG`），
   并点名哪两个块未被校验。

把 `evidenceBudget` 的 `$comment` 换成不含「未被校验」的文字 → 红。

**这一条最值得记的地方**：**"未校验"本身必须写在配置里。**
一个挨着"已被校验的块"的块，会**继承它看起来被守着的印象**。
所以当"加一条校验"做不到时，正确的收尾不是沉默，而是让文件自己说出这件事。

### F-028 · 关键帧缓存**从来没有任何产品代码写入** → 证据包里没有图片，"多模态调用"实际是纯文本

**实现（按已声明的预算，不自定参数）**：

| 部件 | 位置 | 作用 |

| 入缓存 | `TrainingSession.addFramePixels` | 采集侧在把位图交给引擎**之前**调用（所有权转移后就拿不到像素了） |
| 接线 | `App.tsx` 的调度回调 | 先取像素再 `engine.detect`，**不 await** —— 编码不得阻塞采集（红线 9） |

**为什么必须客户端压**：服务端的 `maxRequestBytes`（2 MiB）是**拒绝**而不是降采样，
超了就直接失败。这也让 F-027 里那个"没有任何代码读它"的 `maxImageLongEdgePx`
**真的被读了**。

**验证（可复核）**：

| 层 | 覆盖 |
| --- | --- |
| `apps/web/test/keyframe-capture.test.ts`（10 项）| 缩放尺寸（横图/竖图/不放大/极端窄图不产出 0 高/非法输入返回 null）、抽帧节奏、**编码抛错不冒出**、编码返回 null 不塞空图、sink 为 null 不崩 |

| `apps/web/test/session-groups.test.ts`（3 项）| 给了像素 → 有图 + 无警告；**没给像素 → 必须明确提示**（守住"不静默"）|

**仍未验证的（如实说）**：接上图片**之后建议质量是否变好** —— 那需要真实模型 Key。
热路径开销已用 20 分钟 soak 复测（见 `docs/evaluation-log.md`）。

**对这段新代码本身的边界审查（自查，结论：无需改动）**：

| 边界 | 结论 |
| --- | --- |
| 编码途中用户点了停止 | `stop()` 把 `sessionRef.current` 置 null，而采集器对 `sink == null` **直接返回** —— 那个守卫就是为这条写的 |
| 编码途中会话被换掉（旧编码晚到） | `frameId` 形如 `e{epoch}_t{time}_{seq}`，**带 epoch**，不会跨会话重号；新会话的 `posesByFrameId` 里没有这个 id → `buildKeyframes` 把它归入 `missing`，**无害**（只多一条会被淘汰的缓存项）|
| 采集器计数器跨会话累积 | 采集器在 `start()` 里新建，每个会话一份 |
| 缓存无限增长 | 32 MiB 有界 + FIFO 淘汰；20 分钟 soak 实测堆 4.4→6.2 MiB（含缓存），无增长趋势 |
| 编码失败/尺寸非法 | 返回 `null` → 不塞空图；异常被 `.catch` 吞掉，不冒出到采集循环 |

**顺带记一个门禁的覆盖缺口**：`audit:wiring` 只扫**顶层导出**
（`export function/const/class`），**不扫类的方法**。
所以"一个从来没人调用的公共方法"（`KeyframeCache.add`）它看不见 ——
这正是本条能活到现在的原因之一。该项此前已声明"只覆盖一半"（反向的那一半没自动化），
但"方法级"这个缺口是另一回事，单独记在这里。

### F-029 · 「关键帧必须与挥拍证据对齐」**只在注释里**，而客户端产出的包真的违反它

**日期**：2026-09-16
**分类**：证据（契约约束未执行）+ 测试（两个用例是空的）
**严重度**：中高 —— 它决定模型能引用哪张图；而覆盖它的两个测试**都测不到东西**
**状态**：**已修复**（三处：客户端收窄候选、契约加 `.refine`、两个空用例改成真的）

**怎么发现的**：F-028 把图片链路接通之后，我顺手量了一下"关键帧的 frameId
是否落在它那一板的 `evidenceFrameIds` 里" —— 契约第 33 行写着这是**必须**的。

**实测：18 张关键帧里有 3 张不对齐。**

**三处问题叠在一起**：

| # | 问题 | 说明 |
| --- | --- | --- |
| 1 | **客户端选帧只按时间窗过滤** | `selectRepresentativeFrames` 认为"落在这板的 `[startMs, endMs]` 内"就有资格，而时间窗里还包含**分段器没有收进这一板**的帧（例如开启挥拍前那段准备区驻留）|
| 2 | **契约里那条"必须"只是注释** | `evidencePacketSchema` 里没有任何 `.refine`，`keyframes` 就是个普通数组。契约自己的测试还写着"**这条不是 schema 能强制的**……留给上层参考实现" —— 而那个上层检查**从来没被实现** |
| 3 | **覆盖它的两个用例都是空的** | 见下表 |

**为什么问题 3 最值得记**：

| 用例 | 它声称验证的 | 实际做的 |
| --- | --- | --- |
| `contracts/test/consistency.test.ts` | "关键帧必须落在 evidenceFrameIds 中" | 拿一个**手写好的、本来就对齐**的包去 parse，再断言它对齐 —— 无论 schema 允不允许都通过 |
| `e2e/integration.e2e.ts`「伪造关键帧与挥拍的对齐关系也会被拦下」 | "服务端真的会执行这条检查" | ① **什么都没伪造**：那时包里 `keyframes` 恒为 `[]`，`[].map()` 还是 `[]`；② 通过条件是"被拒 **或** 降级为 `observation_only`"，而 mock 模式**本来就**回 `observation_only` —— 于是它一直"通过" |

**后者是这一批里最坏的一种**：它的名字、注释、断言错误信息都在说
"服务端拦下了"，而它连一个字节的伪造都没发出。
**一个通过条件能在没有该行为时也成立的测试，比没有测试更糟** —— 它产生的是确信。

**这条约束为什么重要**：服务端的 `validate.ts` 会把关键帧 id 并进**可引用集合**
（`knownIds`），于是模型可以引用一张**不属于它正在讲的那一板**的图，
而服务端会认为这个引用合法。

**修法（三处，缺一不可）**：

1. **客户端收窄候选**：`selectRepresentativeFrames` 增加**必填**的
   `evidenceFrameIds`，只从这一板自己的证据帧里挑（时间窗条件保留）。
   传 `[]` 就返回空，**不退回**到"只看时间窗"。
2. **契约把"必须"变成真的**：`evidencePacketSchema` 加 `.refine`，
   不对齐直接判不合法；schema 的注释同步改为"由下面的 `.refine` 强制"。
   客户端已经不会产出不对齐的包，所以正常链路撞不上它。
3. **把两个空用例改成真的**：
   - contracts：对齐→通过 / **不对齐→拒绝** / 无关键帧→通过（三项）；
   - 集成：给夹具加 `withKeyframes` 选项，**先断言包里真的有图**（否则又是空数组），
     再篡改第一张的 frameId，并**只接受"明确拒绝"**（降级不算通过）；
   - 另加一条正向用例：**带图片的包能被真实后端收下** —— 这是图片链路第一次真的走到服务端。

**验证这些断言真的会红**：

| 回退哪一处 | 结果 |
| --- | --- |
| 去掉"只从证据帧里挑" | e2e 报"关键帧里有 **3 张**的 frameId 不在任何一板里" |
| 去掉 `.refine` | 集成用例报"不对齐的包被放行了" |

**顺带翻出的连锁问题（refine 一加就暴露）**：**17 个 API 测试当场变红**，
因为 `apps/api/test/fixtures.ts` 一直在构造**违反契约**的包：

```ts
strokes[0].evidenceFrameIds = ["kf-1", "kf-2", "kf-3"]   // ← 这是**关键帧的 id**
keyframes[i].frameId        = "f-1" / "f-2" / "f-3"      // ← 这才是姿态帧 id
```

把**关键帧 id** 当成了**姿态帧 id** 填进 `evidenceFrameIds` —— 两栏本来就该是同一套
frameId。没有任何东西发现过它。另有一条用例断言"0 次挥拍也合法"，
但它的包**仍带着关键帧**（孤儿图片），按契约不合法；已改成空包 + 新增一条
"0 挥拍却带关键帧 → 拒绝"。

**顺带做过一次"空测试"普查（结论：这一类只剩它一处）**：

思路是把"通过条件在没有该行为时也成立"当成一种可检索的形态，扫了三种：

| 形态 | 扫描方式 | 结果 |
| --- | --- | --- |
| **析取断言** | `expect(... \|\| ...)` | **0 处**（原先那处就是本条修的）|
| **会跳过断言的守卫** | `if (res.ok) { expect(...) }` | 9 处，**逐个看过 —— 全部无害**：每处前面都有一句**无条件**的 `expect(res.ok).toBe(true)`，`if` 只是给联合类型收窄用的。请求真失败时，前一句就会红 |
| **恒真的下界** | `toBeGreaterThanOrEqual(0)` | 有几处（`elapsedMs >= 0` 之类），属于"测不出东西但也不误导"，没动 |

**关键区别**：本条的坏用例之所以坏，是因为它的通过条件是
`rejected || degraded` —— **一个没有无条件锚点的析取**，
两个分支各自都能在不发生被测行为时成立。
而 `expect(res.ok).toBe(true); if (res.ok) {...}` 这种写法有一个无条件锚点，
所以它**不**属于同一形态。把两者混为一谈会去改一堆没问题的测试。

### F-031 · 请求超预算时是**硬 413**，而契约描述的是"先减冗余图片并记录" —— 已按契约实现

**日期**：2026-09-16
**分类**：证据（请求预算 + 降级行为）
**严重度**：中高 —— 超一点预算，用户**什么都拿不到**；而设计意图是"少给几张图，照样给反馈"
**状态**：**已修复**（客户端自动削减 + 如实记录）

**怎么发现的**：F-030 的文档审计里发现 `data-contracts.md` 写着一个**并不存在的行为**：
"上限 2 MiB，**超限先减少冗余图片并记录降采样**"。
而代码是 `analyze.ts` 直接返回 **HTTP 413 + `evidence_too_large`**，
附一句"请减少冗余关键帧或降低图片质量"—— 把这件事**推给调用方**。

**为什么这不是"文档写早了"，而是真缺陷**：413 意味着**拿不到任何反馈**。
而契约描述的降级是"少给几张图 + 如实说明"—— 明显更好，而且是**声明的设计**。
F-028 让图片真的流动之后，这条路径第一次**可达**。

**为什么我一开始没做（以及为什么那是错的）**：我在 F-030 里写过"刻意没有做"，
理由是"会改变送给模型的内容，而本机没有真实模型 Key 可验证效果"。
**这和 F-028 是同一个错**：把"这件事有没有接通"（可验证）和"接上之后建议是否更好"
（需要 Key）混为一谈，然后拿后者去否掉前者。**同一个错在一个会话里犯了两次**，
所以写在这里当警示。

**实现**（`apps/web/src/evidence/evidence-budget.ts` + `completeGroup` 接线）：

| 决策 | 做法与理由 |
| --- | --- |
| 丢哪些 | **从末尾丢**。`selectRepresentativeFrames` 按 引拍→向前→还原→准备→其他 的顺序返回，末尾最不关键 —— 与契约"先减少**冗余**图片"一致 |
| 丢到什么时候 | 直到放得下，或**只剩一张**。一张都不给等于没有图片证据，那还不如让服务端明确 413（失败要明确，不要假装成功）|
| 怎么量体积 | 用**真实序列化结果**（`TextEncoder` 计 UTF-8 字节），与服务端 `Buffer.byteLength(json, "utf8")` **同口径**。估算偏了会算出"压过了"其实没压过 |
| 怎么记录 | 写进 `limitations`（prompt 会带上）**并** `onStatus` 提示。文案里明确要求"涉及画面的结论应相应保守"—— 图少了，结论就该更保守 |
| 预算从哪来 | 客户端持有服务端上限的一份**副本**（2 MiB）。服务端那个可被环境变量覆盖，两处**没有自动比对**（`apps/web` 不依赖 `apps/api`）。所以这是**尽力而为的事前压**：压完仍超时服务端照样 413。这一条写进了模块注释与 `data-contracts.md`，不假装它是保证 |

**验证**：

| 层 | 覆盖 |

### F-032 · 准备区半径**三处各算各的** —— 用户照着调姿势的那个圈，不是状态机用的那个圈

**日期**：2026-09-16
**分类**：指标口径（同一个量多处计算）
**严重度**：高 —— 它直接破坏"照着绿圈调整站位"这个动作，而那正是 F-022 要用户做的第一件事
**状态**：**已修复**（收敛为唯一一处计算）

**怎么发现的**：做 F-022 的阈值诊断时，脚本从"准备区半径 ÷ 配置值"反推体尺度，
得到的却是 **200px**，而同一支素材的遥测报的体尺度是 **155px**。两个数对不上，于是去看谁算错了。

**三处，三个算法**：

| 位置 | 算法 |
| --- | --- |
| 画面上的绿圈（`readyZoneDisplay`）| `readyZoneRadiusBodyScale × (体尺度 ?? 200)` |
| 证据包的 `readyZone.radiusPx` | `readyZoneRadiusBodyScale × **200**`（**写死**）|
| 遥测 `wristToZoneRatio` 的分母 | `readyZoneRadiusBodyScale × 体尺度`（未测到则 null）|

**实测（真实素材）**：体尺度在 **146~250px** 之间浮动，于是三处给出的半径分别是
0.3×200=60、0.3×200=60、0.3×(146~250)=44~75。
**用户照着一个 60px 的圈调整站位，而状态机实际用的是 44~75px 的圈。**

**两个后果**：

1. **界面在骗人**：`readyZoneDisplay` 的文档注释还写着"与分段状态机一致" —— 那是假的。
2. **证据包在骗模型**：`readyZone.radiusPx` 被当作"本组的明确训练约束"发给模型，
   而它与真实约束不符（写死 200 时，误差就是体尺度与 200 的差，这里可达 ±25%）。

**修法**：收敛成唯一一处 —— 新增私有 `zoneRadiusPx()`，
画面、证据包、遥测三者都从它取。体尺度未测到时返回 **`null`**：
**不画圈、包里也不带准备区**，而不是塞一个编出来的半径（红线 1）。

**验证（真实素材）**：修完后从回放数据里量 `zoneRadius ÷ bodyScale`，
**225 帧的取值集合是 `{0.300}`**（此前会随体尺度浮动）。
另加回归 `apps/web/test/ready-zone-radius.test.ts`：用**不等于 200** 的体尺度
（150px → 期望半径 45）断言三者相等 —— 用 200 会正好掩盖这个缺陷。
**已验证：把证据包那处改回写死 200，该测试立刻红**（60 vs 45）。

### F-035 · 诊断脚本第一版在**稀疏尾巴**上给出假"谷底"，对外打出假区间

**日期**：2026-09-16
**分类**：工具（启发式的失效形态）
**严重度**：中高 —— 它输出的不是错数字，是**一个看着像结论的错建议**
**状态**：**已修复**（判据重写 + 单测钉住失效形态）

**第一版的失效**：它在 **1.9~2.0（0 个样本）** 处报"谷底"，
于是打印 **"可行区间 0.3 ~ 2.0"**。而真实分布是**一个宽的单峰**，根本没有两团。

所以它在**任何**稀疏位置都会为真 —— 尾巴上必然报一个。

**用真实数据复跑的结果**：这次它说 **"没找到显著的谷底 —— 这两团之间没有清晰的分界"**，
并明确**不给建议值**，转而说"这种情况更需要人工标注来定段，而不是靠分布"。
**这个答案是"没用"的，但它是真的** —— 而第一版那个"0.3 ~ 2.0"是"有用"的假答案。

**顺带**：为了给这个启发式写单测，把判据从脚本**移进了 `motion-core/src/distribution.ts`**
（脚本目录没有测试运行器）。8 项单测里**四项专门测"它应该说看不出来"的情形**：
单峰分布、稀疏尾巴不算一团、只有一团、以及**实测那支素材的确切分布**
（主峰 + 长肩，远处弱凸起只占 7.6%、够不上 10% 的门槛）——
因为**启发式最危险的失败形态就是"给出一个像结论的数"**。
最后那条把"真实数据正好落在门槛哪一侧"钉住：谁若把门槛调到 5% 好让它"能出个数"，
它会立刻红 —— 而那个数（1.0~1.1 处"谷底"）是编的。

### F-036 · 同一件事实（"这具身体看得清吗"）**两处口径不同** —— 屏幕会画一个它不肯承认看得见的身体的约束圈

它把"我没有去量"当成了"量不出来"。量它是可以做的，而且做了之后结论很干脆。

### F-037 · 红线 7 的守卫被写成了"测试"，实际是**形态启发式**；我试图补一条行为判据，发现它**恒真**

**日期**：2026-09-16
**分类**：验证覆盖（守卫的性质与描述不符）
**严重度**：低（不产生错行为）到中（**让人以为这条红线有人守**）
**状态**：**已澄清**（并**删掉了**我差点留下的那个空测试）

**怎么发现的**：审计 `HANDOFF.md` 的红线表 —— 它说 12 条红线
"大部分已经变成会失败的测试"，并逐条列了"固定它的测试/代码"。
逐条核对到第 7 条（**禁用离线平滑，只用因果滤波**）时对不上：

- 表里写的是 ESLint `no-restricted-syntax` 拦 `.reverse()`
  —— 那是**形态启发式**（扫代码形状），不是行为测试，**也不是测试**；
- 最像行为测试的是 `filter.test.ts` 里那条
  "EMA 按 alpha 收敛，**且不需要未来样本**"。但读下来它断言的是
  **正向一次跑下来的具体数值**（`push(10,10) → 5`）——
  而这些数值**一个非因果实现同样给得出来**。名字里的承诺没有被断言兑现。

**于是我试图补一条真正的判据**：因果性的定义式表述是**前缀不变性** ——
"喂前 k 帧得到的输出序列，必须等于喂全部帧得到的序列的前 k 项"。
我还写了一个**故意非因果**的对照实现，用来证明这条判据**有区分能力**
（不留一个"恒真的准则"）。

**对照失败了 —— 而这次的失败是有价值的**。它"竟然也满足"前缀不变性。
查下去发现根因不是判据写错，而是**结构**：

> 这套滤波器是 **push 即返回、不保留历史** 的 API。
> 第 i 帧的返回值产生的那一刻，第 i+1 帧**还不存在**。
> 所以任何这类实现都必然满足前缀不变性 —— **这条判据在这里恒真。**

也就是说：**红线 7 的保证不是来自测试，而是来自结构**。

（中途还踩了一个小坑，一并记下：对照的第一版写成"边收边算、窗口向右延伸"
—— 它**通过了**判据，因为**它从不回头改写已返回的输出，所以它其实是因果的**。
"看起来非因果"不等于违规。判据没错，是控制组没有真的违规。）

**⇒ 所以我删掉了那个测试文件。** 一个恒真的测试**比没有测试更糟**：
它会让人以为这条红线有人守。这正是 `F-029` 那一类"空测试"的形状，
仓库为此做过一次普查（结论是"这一类只剩 F-029 那一处"）——
而这次普查**落到了我自己刚写的新代码上**，是那个反向对照抓住了它。

**红线 7 现在的真实保证（如实说）**：

| 保证来自 | 挡得住 | 挡不住 |
| --- | --- | --- |
| **结构**：push 即返回、不保留历史 | 任何"回头改写已播报结论"的实现（做不到）| —— |
| ESLint 拦 `.reverse()` | `arr.reverse()` 这类整段反转 | **手工倒序循环**（`for (i = n-1; i >= 0; i--)`）、**"先把帧缓存起来最后统一平滑"** |

并在改动前处理代码时把"**不许缓冲重算**"当成硬约束看。

**没有新增测试**（这是本条的结论，不是遗漏）。

### F-038 · 两个**出厂默认值**在真实模型上都是错的：`max_tokens=400` 必然截断、超时 `4000ms` 正落在中位延迟上

**日期**：2026-09-16
**分类**：配置（默认值与真实提供商不匹配）+ 诊断信息（截断被报成 JSON 错误）
**严重度**：**高** —— 用默认配置接真实模型，**100% 的请求都拿不到反馈**
**状态**：**已修复**（两个默认值按实测改，截断另立错误码）

**背景**：拿到真实密钥后第一次把服务端 live 链路接到真实模型

```json
  "message": "模型返回内容不是合法 JSON",

```

JSON 解析失败？正文看着是好的，只是**在中间断掉了**。

| --- | --- |
| `completion_tokens`（**含推理**）| 398 / 440 / 703 / 736 / 813 |
| 其中正文长度 | 只有约 160~180 个字符 |
| 出厂默认 `MODEL_MAX_TOKENS` | **400** |

| 量 | 实测（ms）|
| --- | --- |
| 短提示单次调用 | min **2278** / 中位 **3928** / max **4753** |

| 项 | 旧 | 新 | 依据 |
| --- | --- | --- | --- |
| `MODEL_MAX_TOKENS` | 400 | **2000** | 实测完成用量（含推理）398~813，真实端到端在 1200 通过；取 2000 留余量 |

按 `AGENTS.md`"改阈值必须记录理由与版本"办。

**修法（诊断，这一半同样重要）**：新增错误码 **`model_truncated`**。

details 里补一句"推理模型会先消耗推理 token…调大 MODEL_MAX_TOKENS 后重试"。
**加这个码时顺手确认了"不误报"**：`finish_reason` 不是 `length` 时仍报
`model_invalid_json`（两条用例各钉一边）。

**修完的验证（用的是代码里发布的默认值，不是探针自己写的值）**：

### F-040 · 导入视频时**同一个文件被播了两遍** —— 界面上的视频停了，骨架还在动（**用户报的**）

**日期**：2026-09-16
**分类**：调度/接线（显示与采集不是同一个源）
**严重度**：高 —— 用户直接看到"画面与分析不一致"，会怀疑识别坏了
**状态**：**已修复**

**用户原话**：「在练习的视频页面中，导入视频，视频已经停止的情况下，框架还在移动」。

**根因**：摄像头那条路是「离屏元素采集 + 界面元素显示**同一路 MediaStream**」，
两边共享一个流，天然同步。**导入视频没有流** —— 原先给它单独
`el.src = handle.video.src`，于是**同一个文件被播了两遍**：

| 元素 | 用途 | `loop` |
| --- | --- | --- |
| 离屏（`createElement("video")`）| 喂分析（rVFC → 推理 → 叠加层）| **true** |
| 界面上的 `<video>` | 只负责显示 | false（默认）|

两者各自计时、互不影响 ⇒ **界面那段播完停住了，喂分析的还在循环**。

**实测（暂停界面视频后 4 秒内的画布绘制调用数）**：

| | 绘制调用 | `clearRect` 频率 | 涉及的 `currentTime` |
| --- | --- | --- | --- |
| 修复前 | **3574** | 31.3 次/秒（间隔中位 33ms）| 1 个（冻结的 4.94s）|
| 修复后 | **26**（全部在暂停后 2ms 内）| 0.3 次/秒 | 1 个 |

那条 `clearRect 33ms` 正好是 30fps —— 视频的帧率，说明喂分析的元素仍在满速产出帧。

**修法**：导入视频时把**采集元素本身**挂进 `.stage`（新增 `videoHostRef` 容器），
**只有一个播放实例**，画面与分析永远是同一帧。摄像头那条路不动。

**回归**：`apps/web/e2e/video-playback.e2e.ts`（需 `PPC_VERIFY_VIDEO`）——
① 结构：`.stage` 里只能有 1 个 `<video>`；② 行为：**暂停后叠加层必须停止变化**。
**已用"改回去"验证**：把两路播放恢复，该用例立刻红，报
「视频已经停了，叠加层还在变 —— 画面与分析又不同步了（F-040 复发）」。

**过程中我自己写错一次**：第一版的等待条件是"指纹不等于 `no-canvas`"，
而哈希每次都不一样 ⇒ 轮询第一帧就返回，白等 3 秒拿到 `nz=0`。
判据改成 `nz>0` 才对。

### F-043 · 指导人工标注的**联系表分辨率不够** —— 照着它标会系统性低报

**日期**：2026-09-17
**分类**：工具（标注辅助物的精度与验收判据不匹配）
**严重度**：中高 —— 它不报错，只会让**唯一的阻塞项**产出偏低的数字，而责任看起来在标注者身上
**状态**：**已修复**（导出时自动自检 + 分辨率可调）

**怎么发现的**：给 `IoU ≥ 0.5` 算完「标注要标多准」（= 单板时长的 25%）之后，
顺手拿这个数去量了一眼现有的标注辅助物：

| | 值 |
| --- | --- |
| 验收判据要求的精度（800ms 单板）| 两端各 **±200ms** |
| 联系表默认格子 | **250ms** |

**格子比容差还粗** ⇒ 标注者再怎么仔细也标不到精度，`eval:replay` 出来的
precision / recall 会**偏低**，而偏低的原因**不在识别、也不在标注者**，
在这张表本身。这种「谁都没错但结论是错的」最容易被当成识别质量问题。

**还有一层**：自检的第一版我拿**已检出的挥拍时长**当基准 —— **那是错的**。
连续对拉时检测会把相邻几板**合并**（F-022），合并后的时长（实测 1900ms / 2200ms）
**长于**真实单板，用它算出的容差偏松（±475 / ±550ms），于是自检会得出「够用」的
**错误**结论 —— 恰好掩盖了它本该发现的问题。基准改取**预期单板时长**
（`PPC_EXPECTED_STROKE_MS`，默认 800ms），并把几个常见时长的容差一并打出来。

**修法**：

- **默认值改由判据推出**：格子 = 容差的一半 = `boundaryToleranceMs(预期单板) / 2`
  （800ms → **100ms**）。一个默认产物过不了自己自检的工具，等于把问题留给用户去发现 ——
  所以不是"改成可配、让用户自己调"，而是**默认就该是对的**；
  仍可用 `PPC_CONTACT_SHEET_STEP_MS` 覆盖；
- 导出时**自动自检**并把结论打给人看，含一张「时长 → 容差」对照表；
- 不够细时**明确写出后果**（「会系统性低报，标不准不是标注者的问题」）
  与两条出路（调小格子重新导出，或直接对着视频标）。

**实测输出**（本机、这支素材）：

```
标注精度自检（联系表格子 250ms）：
  预期单板时长 → 两端各需标在 ±X 内（IoU ≥ 0.5 的几何要求）
    2200ms → ±550ms     1500ms → ±375ms     1000ms → ±250ms
     800ms → ±200ms   ← 自检基准            600ms → ±150ms
  本次检出的挥拍时长：1900ms、2200ms（连续对拉时会被合并，故**长于**真实单板 —— 别拿它当基准）

⚠️ 这张表**不够细**：格子 250ms 粗于 800ms 单板所需的 ±200ms。
   直接用它会**系统性低报**识别质量 —— 标不准不是标注者的问题。
```

**顺带**：`evaluation/samples.json` 的 `step2_annotate` 补了 `precision`（标多准）
与 `contactSheetResolution`（表够不够细）。

### F-044 · 导入的视频**永远播不完** —— 而它与 F-040 是同一行的两次显形

**用户报的**（第一次）："在练习的视频页面中，导入视频，视频已经停止的情况下，
框架还在移动"。**改完 F-040 之后用户又报**（第二次）："视频导入后一直在轮询播放，
反复播放且不会停止"。

两次现象相反，根因是**同一行**：

```ts
// apps/web/src/capture/capture-source.ts
video.src = url;
video.loop = true;      // ← 就是它
```

| | 喂分析的那个 `<video>` | 界面上的 `<video>` |
| --- | --- | --- |
| F-040 **之前** | 离屏元素，`loop = true` | 另一路播放，`loop` 默认 false |
| 用户看到 | 骨架一直在动 | 画面早就停在最后一帧了 |

F-040 把两路合成一路（采集元素**本身就是**显示元素）之后，循环不再有第二个元素
替它"停住"，于是直接显形为"反复播放且不会停止"。

**修完 F-040 还带出第二层**：既然采集元素就是显示元素，`stop()` 里原有的
`URL.revokeObjectURL(...)` + `video.removeAttribute("src")` 就会把用户眼前的
**最后一帧抹成黑屏** —— 而这一刻"本组分析"的请求往往刚发出去，用户正盯着画面等结论。
实测确认：这两行原先对摄像头是对的（轨道本来就停了），对导入视频是错的。

**修法**：
- `loop = false`；新增 `onEnded` 回调（播完**只上报一次**，重复派发不算）；
- `emit()` 在 `ended` 之后**不再喂帧**（回绕/重复回调不该继续进分析）；
- 停止时**保留画面**（`src` 不动），改在**下次导入新素材**时释放上一个 blob URL。

**回归**：`apps/web/test/video-ended.test.ts`（5 项）。把关卡逐个撤掉验证过：
`loop` 改回 `true` → 第 1 条红；去掉播完后的闸门 → 第 3 条红。

### F-045 · 有限素材凑不满 `strokesPerGroup` 时，**一次请求都不会发出去**

用户报的"运行后未看到任何评估结果返回"，第一层是后端没起（F-048），
**这是第二层，而且它不会因为把后端起起来就好**：

成组只在 `validStrokes.length === strokesPerGroup`（默认 3）时发生
（`onStrokeEvent` → `completeGroup`）。而**导入的视频是有限长的** ——
素材不会再给下一帧了，可状态机还在等第三拍。

**实测**：本机真实对拉素材（8.15s / 244 帧）在修 F-046 之前检出 **0 次**挥拍、
修好之后 **1~4 次**。也就是说：**即使分段正常，一段 8 秒素材也常常凑不满 3 次**，
用户拿到的是"什么都没有"，而界面只会说"等待有效挥拍"。

**修法**：`TrainingSession.finishGroup(reason)` —— 素材播完时把已收集的有效挥拍
当一组交出去，并在证据包的 `limitations` 里**写明这组提前结束（N/M）**。
不足额是**事实**，不能让模型把 1 次挥拍当成本组全部表现。
`App.tsx` 在 `onEnded` 里调它，且**顺序不能反**：`stop()` 会 `dispose()` 掉会话，
先停就再也交不出证据了。

**回归**：`apps/web/test/group-finalize.test.ts`（6 项）。也验证过守卫是真的：
把"不足额说明"改成恒不添加，第 3 条（正常凑满的那组不该带这句话）立刻红。

**顺带**：一个夹具被抽成了公共文件（`test/helpers/synthetic-strokes.ts`）。
原先那套"实测调出来的相位序列"只写在 `session-groups.test.ts` 里，
新测试要再用一份就得抄 —— 而"同一个事实两处各写各的"正是本项目反复的坑
（F-017/F-018/F-019）。现在只有一处定义。

### F-046 · 准备区自动标定被**最先到达的那 20 帧**定住 —— 检出次数随标定时刻在 0~4 之间跳

这是"导入视频什么都没有"的**直接原因**，而且它看起来像"识别不行"，实际不是。

准备区是整条分段状态机的**入口**：腕部要先在区内驻留 `readyStableMinMs`，
才谈得上引拍、前挥。而它是**自动标定**出来的（`estimateReadyZoneFromDwell`
取"局部速度最慢的那一半样本的中位数"），标到哪里，后面所有阈值就在哪里生效。

`DWELL_MIN_SAMPLES = 20`（≈0.67 秒）是**估计器能出一个数**的下限，
却被当成了"这个数可信"，于是**最先到达的那 20 帧**决定了整条状态机。
连续对拉里，那 20 帧完全可能整段落在一次引拍上。

**实测**（真实素材 8.15s / 244 帧，腕部行程 506px）：同一段素材、同一套动作，
**只改"从哪一刻开始标定"**：

| 丢弃前 | 标定落点 | 检出 |
| --- | --- | --- |
| 0ms | (641,260) | 2 |
| 1000ms | (599,267) | **0** |
| 2000ms | (680,212) | 4 |
| 2600ms | (442,339) | **0** |
| 3000ms | (632,246) | 1 |
| 4000ms | (697,193) | 2 |

落点散布 **255px**（x），检出 **0~4**。动作一个字都没改。

**修法**（准入条件，不改任何分段阈值）：样本 ≥ **60**（≈2s，跨过至少一个挥拍周期）
**且**相邻两次估计落点差 ≤ **0.1 体尺度**（≈20px，不到半径的 1/3）——
两帧都落在这么近的地方，才说明"最慢的那片区域"不是偶然路过的位置。
急着标定的代价是"整段素材什么都检不出"，多等一秒的代价只是晚一秒开始计数。
对照用的 `calibrateReadyZoneFromMedian` **走同一道门**，否则两者比出来的差异
分不清是估计器不同还是门槛不同。

**复跑实测**：六个时刻的落点从 255px 收敛到 **17px**，检出 **1~4 且无零**，
阶段集合每次都包含 ready→backswing→forward→returning。

**回归**：`apps/web/test/ready-zone-calibration.test.ts`（4 项）。
把闸门关掉 → 前 3 条红。第 4 条（换源要清稳定性记忆）**第一版是空的**：
reset 之后样本本来就是空的，任何实现都返回 0，删掉那行清理测试照样绿 ——
改成"让新旧源估出同一个位置"之后，删掉清理会红（`expected 120 to be +0`）。

**这一条只修了"入口被偶然位置定住"，没有改检出率本身。**
连续对拉下检测合并相邻几板（F-022）仍然存在。

### F-047 · 注释描述了一个**不存在的实现**，并据此推出一个**不适用的理由**

`calibrateReadyZoneFromDwell` 的注释写着：

> 因此把画面切成格子统计落点，取样本最多的那一格（驻留格），再在该格内取中位数细分。
> 停在准备姿势的时间天然远多于挥拍中，所以驻留格就是准备位置。

而实现（`estimateReadyZoneFromDwell`）取的是**局部速度最慢的那一半样本的中位数**，
**全程没有直方图、没有格子**。

不只是"写错了实现"：那句推理**只在有停顿的练习里成立**。连续对拉时手几乎不停，
"停在准备姿势的时间远多于挥拍中"根本不成立 —— 而这正是 F-046 量出来的场景：
标定落点在 442~697 之间乱跳，抓到的往往是挥拍的**端点**（手在那里瞬时最慢）。

已按实现改写注释，并把"连续对拉里可能根本没有驻留位置"写进去。

### F-048 · 后端没起时，前端**只给一句「后端未知」**

用户报的"未看到任何评估结果返回"的**第一层，也是最简单的一层**：后端没在跑。

- `pnpm dev` **只启动前端**（`pnpm dev:all` 才是两个都起）。用户按最自然的命令启动，
  得到的是一个永远不回结论的应用；
- 前端此时只有顶栏一个「后端未知」徽标，**没有任何可行动的信息**；
- 更糟的是健康检查**只查一次**：用户看到徽标、去另一个终端把后端起起来，
  提示却**永远留在那里** —— 除非他想到要刷新页面，而他没有任何理由想到。

**实测确认**：本机 `curl http://127.0.0.1:5173/api/health` 返回 **500**
（vite 代理到 8787 失败，8787 上没有进程）—— 这就是用户看到的现象的成因。

**修法**：`modelMode === "unknown"` 时显示醒目提示，直接给出
`pnpm dev:all` 并点明"只跑 `pnpm dev` 只启动前端"；健康检查**失败会重试**
（3 秒一次，通了就停，不做常驻轮询）。

**没有**把 `pnpm dev` 改成两个都起：一份终端跑 `dev`、另一份跑 `dev:api`
是常见用法，那样改会在第二次启动时撞端口。README 已经把三条命令写清楚了，
所以这里修的是"**看不到**"，不是"命令的名字"。

### F-049 / F-050 / F-051 · 外部评审 R1–R3：三条都复核确认，并已修复

来源：`docs/pingpong-coach-review-and-design.md`（外部只读评审，基线 `fbfb721`）。
按该报告 §12.1 的要求，这里是**先复核、再动手**的结果 —— 逐条在本仓库代码上确认过，
不是照单全收。三条都成立。

**F-049 · 组级肘角把"角度"当成了"时间"（R1）**

```ts
const perStroke = validStrokes
  .map(s => computeElbowAngleAtWristPeak(geoms, s.anchor.timeMs, 80, [...]))
  .map(f => f.value)                 // ← 这是**度**
  .filter(v => v != null);
features.push(computeElbowAngleAtWristPeak(geoms, median(perStroke) ?? first.anchor.timeMs, 80, interval));
//                                                  ↑ 塞进了 anchorTimeMs
```

`median(perStroke)` 是角度（几十到一百多度），却被当成**毫秒**。函数于是去
t≈角度值 附近找几何：通常什么都找不到（→ `null`），偶尔取到一段毫不相干的区间。

**复核方式**：构造"前 1 秒画面无人"（`detected: false` ⇒ 不产生几何）的合成素材，
把挥拍放在后面 —— 这样 t≈角度值 那段必然没有几何。旧实现 `value = null`，
新实现给出本组中位数。旁边那条返回准备区时间的特征写法是对的（中位数进**值**、
锚点单独给），两处一对比就能看出是笔误一类的东西。

**修法**：直接做注释里写明的口径 —— 每板取峰值 ±80ms 的肘角中位数，再对本组取中位数；
不再绕回那个函数（绕回去就还得再给一个时间，而这里根本没有"某一个时刻"）。
缺失时给原因，质量取参与统计的几板里最差的一档。

**回归** `apps/web/test/elbow-group-aggregate.test.ts`（2 项）：一条测"前段无人时仍给出值"，
另一条用 **motion-core 自己的公开函数独立重算**每板肘角再取中位数，把"中位数"这个
语义钉死（只断言"不是 null"的话，改成均值或取某一板都能混过去）。
**改回旧实现两条都红**（第二条的报错正是 `expected null to be close to 178.06`）。

**F-050 · 关键帧的阶段标签全丢（R2）**

`buildKeyframes(ids, cache, poses, role = "other")` 的 `role` 带默认值，
而调用点 `buildKeyframes(candidates.map(c => c.frameId), ...)` 只传了 id 数组。
`selectRepresentativeFrames` 明明算出了引拍/前挥/还原/准备，全部被丢掉。

后果不是"少一个字段"：提示词里写着 `角色=${k.role}`，模型看到六张一律 `other` ——
它没法知道哪张是引拍、哪张在击球附近，于是只能讲"整体节奏"这类没有落点的话。
**这一条直接关系到"模型返回的信息太少"**：不是模型不肯说细，是我们没告诉它每张图是什么。

**修法**：把**默认值本身删掉**，而不是在调用点补一个实参 —— 只要这个参数还能被省略，
下一次改动就会再漏一次。

**回归** `apps/web/test/keyframe-phase-role.test.ts`（1 项）：角色不能清一色 `other`，
且必须各有一张 `forward` 与 `backswing`。**把 `role` 改回 `"other"` 立刻红**。

**F-051 · 挑关键帧时不管有没有图（R3）**

选帧原先拿"时间窗内的姿态帧"当候选、`bytes` 填空数组，挑完才去缓存里找图，
找不到只记一笔 `missing`。而图片**每 3 帧**才采一张（`KEYFRAME_CAPTURE_EVERY_N_FRAMES`），
姿态帧却帧帧都有 —— 两个集合不一样大，于是"挑中的那几张恰好没采图"是常态。

**量化**（合成 3 板、每 3 帧一张图）：旧逻辑在 18 张里报了 **12 张"取不到图"** ——
即**附近明明有可用的图，却白白少发 12 张**给模型。这解释了"模型看到的东西为什么那么少"。

**修法**：候选收窄为"缓存里真的有图"的那些（并带上真实 bytes 与尺寸）；
`missing` 的语义随之回到本意 —— **真的取不到**（编码竞态、调用点被改坏）。

⚠️ **收窄候选会把 F-028 的静默形态重新引回来**：一张有图的候选都没有时，
旧写法会变成"选了 0 张、缺 0 张"，读起来像一切正常。所以另外记一条判断：
**有挥拍却一张有图的候选都没有**时，按"每板"计数并大声报出
（`本组证据不含图片：N 次挥拍的关键帧一张都取不到…`），遥测里的 `keyframesMissing`
也按每板计 —— 宁可数字口径粗糙，也不能让它读成"0 缺失 = 正常"。

**回归** 3 项：每 3 帧一张图时 `keyframesMissing === 0`、每帧都有图时同样为 0，
以及 F-028 那两条（无图时**必须**报出来）保持绿。**改回旧逻辑立刻红**（`expected 12 to be +0`）。

**R4 的半步（已做）**：关键帧的 `role` 名字（`backswing` / `forward` / `return`）很像检出的
**事件**，而实际取的是「区间起点到锚点的中点」这类**按时间比例**的位置。
现在没有事件检测（那是 P1 的事），所以先把实情写进 `limitations`：
「关键帧按挥拍区间的时间比例挑选，不是检出的事件时刻」。
**宁可先说明它是怎么挑的，也不让模型把「名为 forward 的图」当成击球瞬间。**
回归 2 项：有图时必须写；没图时不写（它只在真的有图时才有意义）。

**R5 的前半（已做）**：模型此前只拿到**组级标量**（"本组中位数 880ms"），
这在具体动作上是没有落点的话。而逐板的数**本来就在手里** —— 组级特征的口径就是
"先算每板、再取中位数"，聚合时把每板丢掉了。现在证据包带上 `perStrokeFeatures`
（与挥拍**一一对应**，由契约 refine 强制），提示词里逐板列出"第 N 板 + 起止 + 它自己的数"。

顺带补一个容易漏的地方：**服务端的"可引用 ID 集合"也要收进逐板测量值**。
少收一个来源，模型引用它就会被判"引用了不存在的 ID"，**整条反馈被拒** ——
那是把可用的证据当成攻击来处置。

**这三条对"模型返回的信息太少"的意义**：用户报"模型分析和返回的有效信息有点太少"，
此前我按提示词/契约方向改（加逐条要点、把训练判据喂给模型）。
而 R2/R3 说明还有一半原因在**上游**：模型拿到的图**标签全无、数量还少了一多半**。
提示词再好，也补不回没送到的证据。

### 顺带：反馈新增"逐条要点"，语音提示仍限短

用户要求"把细节逐条列清楚、字数可以略微加长"。做法是**分两个字段**，而不是把
`cue` 写长：

| 字段 | 通道 | 约束 | 为什么 |
| --- | --- | --- | --- |
| `keyPoints` | 屏幕 | 2~5 条，每条 ≤60 字 | 用户要的是"逐条说清楚" |
| `cue` | **语音** | ≤30 字，且只能取自**已审核**提示集合 | 它是**念出来**的，长句子听不进 |

两条约束分开之后各自都能做对；合成一个字段必然要牺牲一边。

服务端把 `keyPoints` 当成**又一个自由文本入口**来对待：
含禁用语的那一条**整条丢掉**（与 `observation` 不同 —— 那是一整段，只能降级后保留原文；
要点是逐条的，丢一行不伤其余），丢掉的条数、原因都写进 `limitations`**说出来**。
回归 6 项。

同时把**本关注点的训练判据**（测量口径 + 门槛）喂进提示词，模型才能说
"超出约 180ms"这种有参照系的话，而不是"回位稍慢"。判据的数值**随证据包发过去**
（`packet.criterion`）而不是服务端自己算：阈值住在 `motion-core`，而依赖方向规定
**服务端只依赖 contracts**（AGENTS.md），服务端再写一份就是同一个事实两处各写各的。

### F-053 · 契约头部把一条**不存在的链路**写成了数据链的一环

`packages/contracts/src/index.ts` 的头部注释写着：

> 数据链：PoseFrame → StrokeEvent → FeatureSet → EvidencePacket → CoachFeedback

而 **`FeatureSet` 这一环是空的**：全仓库除了它自己的定义、这句注释、以及一致性测试之外，
没有任何产品代码**构造**或**读取**它。产品链路直接从 `StrokeEvent` 走到 `EvidencePacket`
（特征是包内的数组）。也就是说，契约的**门面注释**描述了一条比实现多一环的管线。

这与 F-030 同族（"文档说的与代码做的不一致"，而 `check:docs` 结构上查不到叙述性内容），
只是这次出在契约文件自己的头部 —— 而那句话是**新读者理解数据流的入口**，错了代价更大。

**修法**：不改实现（承认它是 P1「逐阶段指标」要用的形状），把注释改成**如实说明这一环尚未接线**。
删掉它反而更糟：下一步就要用它，而且删了以后没人知道它曾经存在过。

**发现方式**：一次只读审计（见下）。这类"声明了没实现"的形状本仓库反复出现
（F-016 定义了却零调用、F-018 算了没有出口、F-027 开关 grep 零引用、F-028 缓存没人写），
所以值得**定期重扫**，而不是等它变成用户可见的故障。

**顺带记下这次审计的完整结论与处置决定**（避免以后重复扫同一批东西）：

| 项 | 判定 | 处置 |
| --- | --- | --- |
| `FeatureSet` / `featureSetSchema` | 无产品代码构造或读取 | **保留形状 + 注释说明未接线**（本文） |
| `IDENTITY_TRANSFORM` / `ImageTransform` | 只有定义，零引用 | **保留**：属 P1 的 ROI/裁剪映射，评审 §6.2 明确要求 |

| `extractHandGeometry` / `FINGER_NAMES` | 只在 `hand.test.ts` 里 | **保留并如实声明**：生产路径确实没用它 —— 这与外部评审的说法一致，已记在 F-006/footnote 里 |
| `featureFlags.*`、`latency.*`、`evidenceBudget` 的部分键 | 运行时零引用 | **设计如此**：`thresholds.json` 是规范快照、不被运行时读取（AGENTS.md），且文件内已自我声明"未被校验" |
| `matchSegments` / `temporalIoU` 等评估匹配 | 仅评估脚本 + 测试 | 拿不准是否仍在使用（未跑脚本），**不下结论** |

把体尺度逐帧记下来，离线才能复算）。审计自己声明了"scripts/*.ts 只统计引用数、未读逻辑"，
错误就出在那一句里。

**抽查 3 条，错了 1 条。** 结论：只读审计**有用但必须复核**，
"没人用"这种判定要看到**引用点的性质**（产品 / 测试 / 离线脚本），不能只看数量。

### F-054 · 证据里只有首尾两端，没有「过程」（外部评审 R4 的实质部分）

**现象**：一板挥拍在证据里只有「从 1200ms 到 1900ms」加几个标量。
模型于是**说不出「引拍拖太久」「前挥来得太晚」** —— 这不是它不肯说细，
是**没人告诉它这一板分几段、每段从何时开始**。

**根因**：分段器**本来就知道**。它每一步都在切换阶段（引拍／前挥／还原），
`enterPhase()` 就是那唯一的漏斗 —— 但那些时刻**从来没被送出去**，
只留在内部状态里。于是"这一板的过程"在证据包门口就被丢掉了，
只剩首尾两端。

**修法**：在 `enterPhase()` **一处**记录事件（不在每个调用点各写一遍 ——
那正是"同一件事写在好几处"的老毛病），闭合时再补一个 `stroke_closed`，
整条序列挂到 `StrokeEvent.phaseEvents` 上：

| 事件 | 何时产生 |
| --- | --- |
| `backswing_start` | 离开准备区（越过有界滞后阈值） |
| `forward_start` | 确认回身 + 距离收缩 + 速度达标 |
| `return_start` | 重新进入准备区 |
| `stroke_closed` | 在区内稳定驻留够久，这一板才算数 |

**几个刻意的取舍**：

- **有序序列，不是固定模板**：一次挥拍可能拉锯（回到区内没稳住、又拉出去重来），
  所以长度不固定、可能重复。契约用 `.refine` 强制 `timeMs` 递增 ——
  顺序错了等于把过程讲反了，而乱序在一维数组里**肉眼看不出来**。
- **每个事件带支撑帧**：拿到时刻之后能回到那一帧去看。这也让「事件定位」与
  「展示关键帧」可以分开评估（评审 §6.2：事件准不准与图清不清晰是两件事）。
- **没有 `confidence`**：分段器**不产出概率**。给一个编出来的 0.8 比不给更糟
  （红线 1 的同一条精神：缺失是「不知道」，不是「不信」）。
- **没有 `method`**：当前只有一种来源，这个事实在证据包的 `limitations` 里说一次就够，
  不必在每个事件上重复。
- **没有触球、没有随挥末端**：检不出来就不假装有（红线 2）。
- **异常结束的那一板带上已经发生的转变，但不补 `stroke_closed`** —— 它没有闭合。

后两条"刻意不放"是同一个教训（与 F-053 同源）：**契约里没有读者的字段就是死字段**。
将来真有了带分数的事件检测器，再加 `confidence` 不迟。

**回归**：分段器 7 项（含反向对照：没离开过准备区就不该冒出 `backswing_start`；
连续两板不互相串）+ 契约 2 项（乱序被拒、空事件合法）+ 会话 2 项 + 提示词 2 项。
**关掉记录、或去掉乱序约束，立刻红。**

**两处被测试纠正的地方**（都不是代码错，是我的前提错）：

1. 第一版用偏移 0.15 / 0.3 就想造出"已经拉开引拍"的中断场景 —— 但那两个值**还在
   有界滞后的缓冲区内**（阈值是半径的 1.2 倍），阶段一直停在 `ready`，
   根本没有引拍转变可记。红了一次才发现我把"在区外"当成了"已离开"。
2. 写测试标题时又用 ASCII 双引号套在双引号字符串里（F-005 同类），
   整个文件解析失败 —— 本会话第三次踩它，已改用 `「」`。

## 待验证能力：手部 21 点（手指细节）

**日期**：2026-09-16
**状态**：代码链路**已实现并在真机验证通过**；**真实素材上的可用性尚未验证**

**做了什么**：姿态模型（BlazePose）每只手只有腕加三个粗点，看不到指节，
因此无法回答"手指在做什么"。新增 `hand_landmarker.task`（7.5 MiB，sha256 已回填
`models/manifest.json`）接入同一 Worker，产出 21 点/手。

**真机验证结论（事实）**：

| 项 | 结果 |
| --- | --- |
| 模型能否加载 | ✅ 能。GPU 委托，初始化 346 ms |
| 关键点集是否正确标注 | ✅ 界面显示 `blaze_33+hand_21`，手部细节"可用（21 点/手）" |
| 真实视频里能否检出 | ❌ **未检出**（`handDetected: false`） |

**为什么没检出 —— 归因是**运动模糊**，不是尺度（这条我先前判错过）**：

我第一版把原因写成"手只占画面宽度 5%，太小"。**那个归因是错的**，
而且会把要解决问题的人引向错误的方向（去换更近的机位）。

实测推翻过程：用**姿态**给出的腕点位置裁出 256px / 384px 的手部区域，
分别放大 1×/2×/3×（最大到 1152px）后跑手部模型 —— **全部 0 检出**。
如果只是尺寸问题，放大就该解决。把裁片存下来目视确认：中心确实是手，
但**手被运动模糊糊成一团，球拍还压在上面**，看不出任何手指结构。

→ 真正的障碍是**挥拍时的运动模糊**。放大恢复不了被快门抹掉的信息。

**为什么姿态不受影响**：同一帧里姿态的右腕置信度是 0.97–1.00（逐帧都检出）。
姿态模型只需定位**肢体大致位置**，对模糊鲁棒；手部模型要靠**手指细节**定位
21 个点，模糊直接抹掉了它依赖的信息。所以"姿态好"不能推出"手部也会好"。

**换清晰图片后模型确实工作**（`PPC_HAND_IMAGE`）：

| 图片 | 手数 | 左右手分 |
| --- | --- | --- |
| 角色设定图 A | **1** | 0.97 |
| 角色设定图 B | **1** | 0.93 |
| 角色设定图 C | **1** | 0.99 |

→ 模型在本机确实能检出人手。
**但这并不等于"手部能力不可用于这段素材、原因在素材而不在代码"** ——
那句话在当时（只拿这一张图对比）看着合理，补测后证明**是错的**：
代码里另有两个各自独立、又都静默的缺陷（F-020 / F-021）。
"素材不够好"与"代码是坏的"是两件事，不能用一个盖住另一个。

**要让手部可用，需要的是拍摄条件**：提高快门/增加光照以冻结挥拍动作，
让手在每一帧里是清晰的（而不是靠拉近机位）。

**但这次曝光了一个我自己的真缺陷（已修）**：手部模型的 `visibility`
**恒为 0** —— 即使左右手分 0.97 的手，21 个点的 `visibility` 也全是 0。
而我把它当可见性用：

```ts
visible: lm.visibility == null ? null : lm.visibility > 0   // 恒为 false
```

后果是**全链路静默失效**：所有手部点被标成 `visible: false`，于是
`extractHandGeometry` 的 `findPoint` 把它们全部过滤掉（几何永远算不出、
永远返回"缺失"），`drawHand` 也一个点都不画。**手部能力等于没接**。

**修法**：`pose.worker.ts` 拆成两个适配函数，语义按模型分别定：

- `poseToPixel` —— 姿态模型的 `visibility` 是有效的遮挡指标，照常用；
- `handToPixel` —— **不读 `visibility`**，置信度记 `null`（"模型没给这个信息"），
  检出与否由"这只手是否出现在结果里"决定。

关键纪律：**"模型没给这个信息"与"确认为不可见"必须可区分** —— 前者记 `null`，
后者才是 `false`。

**回归**：
- `motion-core/test/hand.test.ts` 2 项：`visible: null` 时几何**照样算出**；
  `visible: false` 时才判缺失（两者可区分）。
- `apps/web/e2e/hand-model.e2e.ts`：对手部可辨的真实图片断言检出、坐标有效，
  并**把"visibility 恒为 0"这个事实固定在测试里** —— 若上游哪天开始填它，
  这条会失败，提示去重新审视适配层，而不是删掉断言。

**仍未验证**：真实**挥拍视频**里手部能否稳定检出（现有一支素材因尺度/模糊不行），
以及指关节角度的稳定性。需要一段手部占比更大的素材。
（**补测见本节末**：检出率已量出，且当时"原因不在代码"的判断被推翻。）

**已实现的诚实行为（这部分是达标的）**：

- 手部模型是**可选增强**：它加载失败或逐帧检测失败时，姿态链路照常运行，
  界面明确显示"手部细节：不可用"，不会假装手指细节在跑。
- 没有手部点时一律按**缺失 + 原因**处理（`extractHandGeometry` 返回
  `reasonIfMissing`、各项为 `null`），**不用 0 或默认姿态顶替**。
- 手部左右分配用**姿态腕部位置**做锚点，不用 MediaPipe 的 `handedness` 标签
  （该标签依赖"输入是镜像自拍图"的前提，导入视频不成立）；超出容差的手
  **不分配**——宁可不给，也不给错的。

**红线 3 的落实**：手部点**只用于测量**可见的指关节几何
（`fingerFlexionDeg`、`thumbSpreadDeg`），**不**推断拍面朝向或握力 ——
单目二维确定不了这些。`hand.test.ts` 里有一条断言显式检查输出对象
不含任何 `racket|paddle|face|grip|orientation` 类字段，防止后续"优化"越线。

**要让它真正可用，需要的是拍摄条件，不是改代码**：

- 手部（至少持拍手）在画面中占据**显著比例**——建议持拍侧半身入画，
  而不是全身远景；
- 避免把挥拍动作拍糊（提高快门 / 增加光照）。

### 补测（2026-09-16）：检出率已量出，且上面那个结论被推翻

用同一支素材逐帧采样（步长 0.25s，共 31 帧；`PPC_VERIFY_VIDEO`）：

| 项 | 实测 |
| --- | --- |
| 手部检出率 | **2 / 31 帧**（t≈3.0s、t≈6.25s），其余 29 帧 `handDetected: false` |
| 检出时手的尺度 | 包围盒对角线约 **91 px**（画面宽 1280） |
| 检出之后的可用性 | 修 F-020 / F-021 **之前**：完全不可用（点被丢弃，且画不出来） |

**更正一句我先前写错的话**：本节原先写着"要让它真正可用，
需要的是拍摄条件，**不是改代码**"。补测证明**这句话有一半是错的** ——
代码里有两个各自独立的缺陷（F-020 单位口径、F-021 绘制），
在它们修好之前，**再好的拍摄条件也不会有任何手部输出**。

**仍未验证（这一段才是真正的未知）**：

- 那 2 帧里，t≈6.25s 的"手"**画在了人脸/下巴上** —— 从放大图看是**误检**，
  那里没有手。而手部模型**不提供逐点置信度**，下游**没有任何办法**
  识别并拦下这种误检。这是本能力目前最实质的风险。

- 所以**检出率与正确率都还没有可信数据**。要得到它们，需要一段手部清晰、
  且**带人工标注**的素材（B4）。

**下一步**：不要基于现有素材给出手指层面的任何结论；也不要只凭
"模型加载成功"就说手部可用。界面上的"可用"目前只表示**模型加载成功**。
