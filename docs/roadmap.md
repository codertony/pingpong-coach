### 接线审计：为什么值得进 CI

这一批修的缺陷里，**最值得警惕的不是"算错了"，而是"根本没被调用"**：

| 缺陷 | 形态 |
| --- | --- |
| F-016 第一层 | `computeElbowAngleAtForwardPeak` 定义了、导出了、**有测试**，但产品代码零调用 —— 而它对应界面里**用户可选**的关注点 |
| F-016 第二层 | mock 适配器忽略 `packet.focusId`，对任何关注点都讲返回准备区时间 |

这类问题的共同点：**测试全绿也说明不了任何事**。测试断言的是函数行为，
而零调用的函数，它的测试再完备也不影响产品。

`pnpm audit:wiring` 固化**正向**那一半：列出 motion-core 的运行时导出，
逐个在产品代码（`apps/*/src`、`knowledge/`、`configs/`）里搜调用点；
**零调用且不在豁免清单里 → 门禁失败**。

**豁免清单必须写明理由**（`scripts/audit-wiring.mjs` 的 `ALLOWED_UNWIRED`）：
它是"我们明知这些符号当前无人调用、并且接受"的书面记录，不是让检查通过的开关。
清单**过期也报错**（符号已被调用或已不存在），否则后来的人会被它误导。

**已验证脚本能真的抓住缺陷**（不是写了个永远通过的东西）：

- 拿掉一条豁免 → 报 `extractHandGeometry` 未登记，退出码 1；
- 放一条不存在的豁免 → 报该条失效，退出码 1；
- 正常情况退出码 0。

**只查运行时导出**（`function` / `const` / `class`），**不查 `interface` / `type`** ——
类型的"被使用"发生在编译期，用文本搜调用点没有意义，混进来只会淹没真信号。

### A7 的四个坑：只有真实构建才会暴露

我先前把 A7 记成"本机没有 docker，无法执行"。**那个判断错在查得太窄** ——
本机没装 `docker`，但**装着 Podman**（5.7.1，WSL machine 常驻运行）。
换成 `podman build` 之后真跑了一遍，四个问题**全部只在真实构建里暴露**：

| # | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| 1 | `corepack` 拉 pnpm 失败：`ECONNREFUSED 127.0.0.1:17890` | 宿主有自己的本地代理，构建环境把它注入了容器；而**容器里的 `127.0.0.1` 是容器自己**，不是宿主 | 在 builder / prod-deps 两阶段显式清空 `HTTP(S)_PROXY`；容器本身能直连 registry（实测 npmjs 与 npmmirror 都 200） |
| 2 | `prod-deps` 阶段 `sh: husky: not found` → `ELIFECYCLE` | 根的 `prepare` 脚本调 husky，而 `--prod` 不装 devDependencies | `pnpm install --prod --ignore-scripts`。husky 只给本地 git 钩子用，镜像里无意义 |
| 3 | 启动报 `Cannot find module '/app/node_modules/.bin/tsx'` | `tsx` 声明在 `apps/api` 的 dependencies 里，pnpm 装在 `apps/api/node_modules/`，**不在根** | CMD 路径改为 `apps/api/node_modules/...` |
| 4 | 启动报 `SyntaxError: missing ) after argument list`，指向 `.bin/tsx` | `.bin/` 下是**给 shell 用的包装脚本**（`#!/bin/sh`），交给 `node` 跑会被当成 JS 解析 | 直接指向真实入口 `tsx/dist/cli.mjs`，绕开 `.bin` |

**一条值得记住的推论**：坑 4 是"在 Windows 宿主上装依赖、把 `node_modules` 复制进
Linux 镜像"这个做法的症状。它在**纯 JS 依赖**（本项目全部是）下能跑通 ——
容器实测正常服务。但若将来引入**原生模块**（node-gyp / 预编译二进制），
宿主装的版本与镜像平台不匹配，会在运行期报错。那时应当改成
**在容器内 `pnpm install`**（例如用 `pnpm deploy` 产出可移植的依赖树），
而不是继续复制宿主产物。

### A2 的红线 8 用例：先判断"不值得"，重审后做成了

`validateModelOutput` 的伪造引用拦截（红线 8）只有让请求走到**模型调用之后**
那一段才测得到，而 mock 模式根本不经过模型调用。要覆盖它得额外搭三样东西：
一个 live 模式的 API 实例、一个返回伪造输出的假供应商、以及一条让前端能打到
第二实例的转发路径。

**第一次尝试失败并被我回退了**：当时想借 vite 代理转发，卡在前缀改写上
（`/api-live` 会被 `/api` 规则先匹配走；这个版本的 `rewrite` 与 `bypass`
行为都与预期不符）。我据此判断"边际价值抵不上常驻复杂度"。

**后来重审发现那个判断是错的** —— 我把"vite 代理做不到"当成了"这件事做不到"。
换成 60 行的独立转发服务（`scripts/e2e-stage2-proxy.mjs`）后，
前缀剥离完全由自己控制，一次就成了：

- `scripts/e2e-fake-model.mjs` —— 假供应商，返回 schema 合法但
  `evidenceRefs` 指向不存在 ID 的输出；
- `scripts/e2e-stage2-proxy.mjs` —— `/stage2/*` → live 实例，自带 CORS；
- Playwright 起 5 个进程（假供应商 / live 实例 / 转发 / mock 实例 / vite）。

服务端实际返回 `evidence_ref_unknown`，并附带 `reference_not_reviewed`
（红线 4 也一并拦下）—— 正是这条用例要钉住的行为。

**一处实测踩到的细节**：假输出必须**整体通过 schema**，只在 `evidenceRefs` 上作假。
第一次少了 `limitations`，被 `model_invalid_json` 提前拦下，用例就测不到
红线 8 真正要测的那条了。

**教训**：把"某个工具做不到"当成"这件事做不到"，是最容易自我说服的偷懒方式。

也就**无法回答"这个产品到底准不准"**。这是最关键的一步。

---

## 五、未完成 —— 必须你主观判断（C 类）

| # | 项 | 为什么我不能替你判断 |
| --- | --- | --- |
| C1 | 建议文案是否像真教练说的 | 逻辑对 ≠ 话说得对。"肘角偏小"和"你击球时手肘太收，试着打开一点"是两种产品 |
| C2 | 播报时机与频率 | 提示太晚没用、太频繁烦人 —— 这是体感问题 |
| C3 | 反馈是否可执行 | 用户看完知道下一板怎么改吗？ |
| C4 | 整体交互顺手度 | 准备区提示是否明显、界面是否好懂 |
| C5 | 是否愿意持续用 | 最终的产品判断 |

**建议做法**：跑一轮真实训练，边打边记"哪里让我停下来迷惑了"。这类反馈比任何测试都有价值。

## 六、红线自检（这些我已在代码里固定，你只需知道）

这些是方案里明确的安全约束，我写成了**测试断言**，改坏了 CI 会红：

| 红线 | 固定方式 |
| --- | --- |
| 缺失值不得填 0 | `null` + `reasonIfMissing`，`prompt.test.ts` 断言缺失值绝不渲染成 `0` |
| 未审核规则只能观察 | `knowledge.test.ts` 断言必须 `status === "reviewed"` **且** `referenceId != null` |
| Mock 必须可见 | `/api/health` 返回 `mock` 标记，页面状态栏显示 |
| 不得自动重试 | `provider.test.ts` 断言超时时 `fetch` **恰好调用 1 次** |
| 服务端二次校验 | `validate.test.ts` 拦截会返回 5xx 的场景，改为 `httpStatus: 200` 的降级响应 |
| 因果过滤 | 未通过因果检验的特征不进入建议 |

## 七、我建议的推进顺序

```
1. 你跑 B1（模型下载 + 目视验证）        ← 10 分钟，解锁整条视觉链路
2. 我做 A1 / A2 / A5（组件、串联、错误路径）
3. 你跑 B4（真实素材），我们按 F-00x 逐条记失败
4. 你走 C1–C5，我按反馈改文案与交互
5. 重复 3–4，直到质量稳定
```

**为什么这样排**：B1 挡在最前面 —— 没有它，后面所有关于"识别准不准"的讨论都是空谈。
