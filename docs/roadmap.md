## 一、判断标准：什么情况下需要你介入

我把工作分成三类，介入成本完全不同。

| 类别 | 判据 | 谁来做 |
| --- | --- | --- |
| **A 类 · 代码正确性** | 只要能跑代码就能判定对错 —— 类型、边界、协议、几何、状态机 | **我在沙箱做完**，用测试固定住 |

| **C 类 · 主观判断** | 需要"人觉得对不对" —— 文案是否自然、建议是否像教练说的、交互是否顺手 | **必须你判断**，我只能保证逻辑自洽 |

**关键结论**：A 类我已经清空；B 类只剩 1 项（F-006 模型下载）；C 类**必须**由你走一遍，
因为它是这个产品唯一无法用断言表达的部分。

### A7 的验证边界：哪些验了、哪些没验

本机没有 `docker`，所以**镜像本身从未构建过**，不能当成已验证。但镜像依赖的
每一环都用能在本机执行的等价命令逐条验过：

| 验证项 | 方式 | 结果 |
| --- | --- | --- |
| 运行时环境变量是否够用 | 按 Dockerfile 的 `ENV` 起服务（`KNOWLEDGE_DIR` / `WEB_DIST` 用绝对路径） | ✅ `/api/health` 200 |
| API 能否托管前端产物 | 同上，请求 `/` | ✅ 200（`fastifyStatic` + SPA 回退生效） |
| 模型资产是否可服务 | 请求 `/models/pose_landmarker_full.task` | ✅ 200 |
| wasm 运行时是否可服务 | 请求 `/wasm/vision_wasm_internal.js` | ✅ 200 |
| 知识文件能否被读到 | `POST /api/coach/analyze` | ✅ 返回受校验的反馈 |
| `tsx` 在 `--prod` 下是否还在 | 见下 | ✅ 已修 |

**顺带修掉一个真问题**：`tsx` 原先列在 `apps/api` 的 `devDependencies` 里，
而它是 `start` 脚本实际使用的**运行时启动器**。`pnpm install --prod` 会把它剪掉，
生产镜像里服务根本起不来。已移到 `dependencies`。

**没验的**：镜像构建本身、镜像体积、容器内非 root 用户的文件权限、
`HEALTHCHECK` 在编排里的行为。这些都要有 docker 才能验，**不要当成已验证**。

### A2 的红线 8 用例：先判断"不值得"，重审后做成了

`validateModelOutput` 的伪造引用拦截（红线 8）只有让请求走到**模型调用之后**
那一段才测得到，而 mock 模式根本不经过模型调用。要覆盖它得额外搭三样东西：
一个 live 模式的 API 实例、一个返回伪造输出的假供应商、以及一条让前端能打到
第二实例的转发路径。

**第一次尝试失败并被我回退了**：当时想借 vite 代理转发，卡在前缀改写上
（`/api-live` 会被 `/api` 规则先匹配走；这个版本的 `rewrite` 与 `bypass`
行为都与预期不符）。我据此判断"边际价值抵不上常驻复杂度"。

**后来重审发现那个判断是错的** —— 我把"vite 代理做不到"当成了"这件事做不到"。
换成 60 行的独立转发服务（`scripts/e2e-stage2-proxy.mjs`）后，
前缀剥离完全由自己控制，一次就成了：

- `scripts/e2e-fake-model.mjs` —— 假供应商，返回 schema 合法但
  `evidenceRefs` 指向不存在 ID 的输出；
- `scripts/e2e-stage2-proxy.mjs` —— `/stage2/*` → live 实例，自带 CORS；
- Playwright 起 5 个进程（假供应商 / live 实例 / 转发 / mock 实例 / vite）。

服务端实际返回 `evidence_ref_unknown`，并附带 `reference_not_reviewed`
（红线 4 也一并拦下）—— 正是这条用例要钉住的行为。

**一处实测踩到的细节**：假输出必须**整体通过 schema**，只在 `evidenceRefs` 上作假。
第一次少了 `limitations`，被 `model_invalid_json` 提前拦下，用例就测不到
红线 8 真正要测的那条了。

**教训**：把"某个工具做不到"当成"这件事做不到"，是最容易自我说服的偷懒方式。
